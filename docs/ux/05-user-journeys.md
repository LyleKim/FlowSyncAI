# 05. 핵심 사용자 흐름 (Journeys)

입력: `00-context.md`, `01-strategy.md`, `02-data-feasibility.md`, `03-current-ui-inventory.md`. 방법론: Intent `/journey`.
범위: 사용자가 보고 하는 것만 설계한다. 정확한 화면 배치는 `/wireframe`, 내비게이션·라벨은 `/organize`(`04-information-architecture.md`), 문구는 `/articulate`, 예외 경화는 `/fortify`가 맡는다.
시각화: 호출자가 산출물을 이 마크다운 한 파일로 지정해 HTML/Figma 질문은 생략했다. 아래 §0의 텍스트 흐름도로 대신한다.

**근거 강도**: 사용자 조사는 0건이다. 흐름은 (a) 사용자가 말한 목적 2개, (b) 02의 데이터 사실, (c) GitHub 동작에 대한 내 이해에서 나왔다. (c)는 "(확인 필요)"로 표시했다. 화면 이름은 04와 충돌하지 않도록 **임시 이름**(괄호 안 `S-`코드)으로 부른다.

## 0. 한눈에 보기

```
            [처음 방문]                         [매일]                          [가끔, 주 몇 번]
   J1 처음 설정 ───────────► J2 리뷰어의 하루 ◄──── 영역 칩 ────► J3 프로젝트 흐름 이해
   로그인 입력                 열기→큐→우선순위→                      영역 개요→영역 상세→
   → (레포 추가) → 첫 동기화    GitHub 리뷰→복귀→상태 갱신              대기 PR 신호 확인
        │                         │            │                         │
        └──────── 모든 흐름 위에 J4 (오류·빈 상태·오프라인·동기화 실패·빈 영역) ────────┘
```

- J2는 앱의 **첫 화면이자 매일 열게 만드는 이유**(전략 가정 A1). J3은 **차별점**(전략 §1 Q5).
- J2↔J3는 두 군데에서 이어진다: 큐 행의 "영역" 칩 → 영역 상세, 영역 상세의 "대기 중인 PR" → 해당 PR(내가 리뷰어면 큐의 같은 행).
- 사용 리듬이 다르므로 한 화면에 섞지 않는다(전략 Q3).

### 공통 전제(확정 결정 + 02에서 가져옴)

| # | 전제 | 출처 |
|---|---|---|
| P1 | "나" = 브라우저 `localStorage`에 저장한 내 GitHub 로그인. 인증 없음. 비교는 소문자 정규화 | 00 결정 1, 02 §1-4 |

| P7 | 영역 시각화는 "활동"이다(진행이라 부르지 않음). 대기 PR 수·최장 대기를 얹는다 | 00 결정 5, 01 §3 |
| P8 | localStorage 오프라인 폴백은 정리 대상 | 00 결정 4 |

### 큐에서 PR이 가질 수 있는 상태 (모든 흐름이 쓰는 어휘, 가설)

| 상태 | 뜻 | 내 큐에서 | GitHub 신호 |
|---|---|---|---|
| 대기 | 내가 리뷰어로 지정됨, 아직 리뷰 안 함 | 맨 위, 대기 시간 순 | 열림, 내가 `requested_reviewers`에 있음 |
| 다시 요청됨 | 리뷰한 뒤 작성자가 재요청 | 대기에 합류, "다시 요청됨" 표시 | 요청 목록에 다시 나타남 |
| 내가 리뷰함 | 리뷰를 냈고 작성자 응답 대기 | 접힌 그룹 | 열림, 내가 요청 목록에서 빠짐 + 내 리뷰 있음 |
| 정리됨: 머지/닫힘/요청 취소 | 더 할 일 없음 | "정리됨" 그룹에 이유와 함께 N일 보관 후 사라짐(N 가정: 7) | `merged`/`closed`/요청 목록에서 빠짐+내 리뷰 없음 |

(확인 필요) GitHub는 리뷰를 제출하면 그 사람을 요청 목록에서 뺀다고 알고 있으나 코멘트만 남긴 경우까지 같은지는 검증하지 않았다. 틀리면 "내가 리뷰함"을 `/pulls/{n}/reviews`로만 판정해야 하고 호출이 늘어난다.

## 1. J1 처음 설정

### 1.1 문제와 성공

- **사용자 목표**: "내 리뷰 요청이 여기 뜨는지 확인하고 싶다." 설정 자체는 목표가 아니다.
- **성공**: 앱을 처음 연 뒤 **3단계 이내(로그인 입력 → [레포 추가] → 큐 확인)** 에 내 리뷰 대기 PR이 목록에 보인다. 시간 목표 60초는 가설(기준선 없음).
- **현재 마찰**: 로그인 입력 지점이 감시 레포 추가 모달 안뿐이고(`WatchedReposPanel.tsx:32,53`), 가치(내 PR)를 보기 전에 레포 URL부터 요구한다. "나" 개념이 UI에 없다(00 P0).

### 1.2 변형

| 변형 | 상황 | 차이 |
|---|---|---|
| **J1-a 첫 사람** | 서버에 감시 레포가 0개 | 로그인 입력 → 레포 추가 → 첫 동기화 3단계 모두 필요 |
| **J1-b 합류자** | 팀이 이미 레포를 등록함(예상되는 대다수 경우, 2번째 사람부터) | 로그인 입력만. 레포 추가를 **건너뛰고** 바로 첫 동기화. "이미 N개 레포를 감시 중"을 보여준다 |
| J1-c 기기 변경 | 같은 사람이 다른 브라우저 | J1-b와 같고 로그인만 다시 입력(기기 간 동기화 없음, 02 §1-4) |

J1-b가 흔한 경로인데 현재 구조는 이를 지원하지 않는다(P3). 이 가정이 틀려 팀이 "각자 서버를 띄우는" 경우면 J1-a만 존재한다(01 §7 질문 1, 미해결).

### 1.3 단계표

| # | 사용자 목표 | 화면에 보이는 것 | 행동 | 피드백 | 실패 지점 | 복구 |
|---|---|---|---|---|---|---|
| 1 | 앱이 뭘 하는지 알고 내 신원을 알려준다 | 한 줄 설명("리뷰 요청된 PR을 모아 보여줍니다"), GitHub 로그인 입력 1개, 후보 칩(서버에 이미 있는 `WatchedRepo.githubLogin`/PR 작성자 로그인, J1-b에서만), 하나뿐인 주 버튼 | 로그인을 입력하거나 후보를 고른다 | 입력 중 소문자 정규화 미리보기, 후보 선택 시 즉시 채움 | ① 오타·대소문자 ② 내 로그인을 모름 ③ 후보가 없음(J1-a) ④ 존재하지 않는 로그인 | ① 정규화 + 5번에서 "0건"일 때 로그인 확인 안내(J4-E5) ② 도움말 한 줄: "github.com/ 뒤의 이름" ③ 직접 입력 ④ 존재 확인은 `GET /users/{login}` 필요 → 백엔드 의존(확인 필요), 없으면 첫 동기화에서 발견 |
| 2 | (J1-a만) 감시할 레포를 알려준다 | 레포 URL 입력, 예시 형식 `github.com/owner/name`, "이 레포에서 내게 온 리뷰 요청을 가져옵니다" | URL 입력 후 추가 | 추가 즉시 행 생성 + "가져오는 중" | ① URL 형식 오류 ② 비공개 레포·서버 토큰 권한 없음 ③ 서버 `GITHUB_TOKEN` 미설정 ④ 이미 등록됨(409) | ① 인라인 검증, 입력 유지 ② 원인과 다음 행동("서버 토큰이 이 레포를 읽을 수 없어요. 서버 관리자에게 토큰 권한을 요청하세요") ③ 동일, 관리자 안내 ④ 오류가 아니라 "이미 감시 중이에요" + 계속 진행 |

| 5 | (선택) 프로젝트 흐름도 있다는 걸 안다 | 큐가 비었을 때만 보조 링크 "프로젝트 흐름 보기" | 클릭 | - | - | - |

### 1.4 인지 워크스루 (4질문)

질문: ① 사용자가 올바른 효과를 내려 하는가 ② 올바른 행동이 눈에 띄는가 ③ 그 행동이 원하는 효과와 연결돼 보이는가 ④ 행동 후 진전을 알려주는가. 판정 ○ 통과 / △ 위험 / × 실패.

| 단계 | ① | ② | ③ | ④ | 메모 |
|---|---|---|---|---|---|
| 1 로그인 입력 | △ | ○ | △ | ○ | 사용자가 원하는 건 "내 PR 보기"인데 첫 화면이 입력 폼이라 가치 전에 요구가 온다. 왜 필요한지 한 줄 필수 |
| 2 레포 추가 | ○ | ○ | △ | ○ | "감시 레포"는 내부 용어. 사용자 말로는 "리뷰 요청을 가져올 레포" |
| 3 첫 동기화 | ○ | - | - | △ | 시간이 걸리면 진전이 안 보임. 레포별 진행 표시 필요 |
| 4 결과 | ○ | ○ | ○ | ○ | 0건 해석이 문제(E5) |

### 1.5 측정(가설)
첫 방문에서 큐 도달까지 소요 시간, 입력 후 0건이 나온 비율(로그인 오타 신호), J1-b 비율. 개인 식별 없는 집계 또는 인터뷰로 대체 가능(데이터 최소 수집).

## 2. J2 리뷰어로서의 하루

### 2.1 문제와 성공
- **사용자 목표**: "지금 내가 막고 있는 PR이 뭔지 알고, 무엇부터 볼지 정하고, GitHub에서 처리하고, 처리됐다는 걸 확인한다."
- **성공**: 앱 연 뒤 **5초 안에** "내 대기 PR 수와 가장 오래된 것"을 답한다(H1 신호). 리뷰 후 복귀 시 **수동 조작 없이** 상태가 바뀌어 있다.
- **전략적 위험**: 리뷰 자체는 GitHub에서 한다. 이 앱은 **앞뒤**(무엇을, 어떤 순서로 / 했는가)만 다룬다. 앞뒤가 GitHub 알림보다 나은 이유가 없으면 이 흐름은 쓰이지 않는다(가정 A1).

### 2.2 변형

| 축 | 변형 | 차이 |
|---|---|---|
| 진입 | 북마크로 열기 / 탭 복귀 / (후속) 알림 링크 | 탭 복귀는 즉시 재동기화 |
| 큐 규모 | 0건 / 1~5건 / 10건 이상 | 0건은 J4-E7, 10건 이상은 우선순위 보조가 필요 |
| 리뷰어 수 | 나 혼자 / 여러 명 | 여러 명이면 "다른 리뷰어 N명 중 M명 완료"가 우선순위에 영향 |
| 기기 | 웹 데스크톱 기본. 모바일은 이번에 읽기 전용 확인 정도(추측, 사용 맥락 미확인) |

### 2.3 단계표

| # | 사용자 목표 | 화면에 보이는 것 | 행동 | 피드백 | 실패 지점 | 복구 |
|---|---|---|---|---|---|---|
| 1 | 열자마자 내 대기 현황 파악 | 큐 첫 화면. 요약 한 줄: "리뷰 대기 3건 · 가장 오래된 2일". 마지막 확인 시각("방금 확인"). 로그인 표시(내 계정 확인용) | 앱 열기 | 열면 즉시 동기화, 스켈레톤 후 목록 | ① 이전 데이터가 먼저 보여 오래된 걸 믿음 ② 동기화 실패 | ① 항상 "N분 전 확인" 표시, 3분 초과 시 강조 ② J4-E3 |
| 2 | 무엇이 있는지 훑는다 | 대기 그룹의 행 목록. 행마다: PR 제목, 레포·번호, 작성자, **대기 시간**, 변경 규모(+/-, 파일 수), 영역 칩(최대 2개 + "외 N"), draft 표시, 다른 리뷰어 진행 | 스크롤·읽기 | 대기 오래된 순이 기본 | ① 한 PR이 여러 영역에 걸쳐 칩이 넘침 ② 변경 규모 데이터가 아직 없음 ③ draft가 큐를 어지럽힘 | ① 칩 상한+툴팁 ② "알 수 없음"으로 표시(0으로 위장 금지) ③ draft는 접힌 그룹이 기본(가정, 질문 Q4) |
| 3 | **우선순위를 정한다** | 같은 행의 신호: 대기 시간, 크기, 영역, 다른 리뷰어 진행, "다시 요청됨". 정렬 전환(대기 시간/크기/영역). 영역 필터 | 정렬 바꾸기, 행 펼쳐 상세 보기(변경 영역 목록, PR 설명 일부) | 정렬 즉시 반영, 선택 정렬 유지 | ① 어떤 기준이 맞는지 모름 ② "긴급" 같은 작성자 의도가 안 보임 ③ 압박 UI(빨간 경고, 불꽃) 유혹 | ① 기본값 하나(대기 오래된 순)로 시작, 설명은 정렬 라벨에 한 줄 ② GitHub 라벨 저장은 후순위(02 §4-3), 지금은 없음 ③ 거부(조작 패턴 금지). 대기 시간은 숫자로만, 색 강조는 한 단계 |
| 4 | GitHub로 가서 리뷰한다 | 행의 주 행동 "GitHub에서 리뷰"(새 탭), 보조로 제목 링크 | 클릭 → GitHub 새 탭 | 클릭한 행에 "GitHub에서 여는 중" 대신 바로 이동. 행은 변하지 않음 | ① 팝업 차단·로그아웃된 GitHub ② PR이 삭제·권한 없음(404) ③ **이 앱을 떠남**: 돌아올 때 어디까지 했는지 맥락 소실 | ① 일반 링크이므로 영향 적음 ② 앱에선 알 수 없음. 복귀 후 동기화가 정리 ③ 같은 탭이 아닌 새 탭이라 앱 탭이 남아 있음. 복귀 시 단계 5로 |
| 5 | 돌아와서 반영 확인 | 탭 복귀 시 자동 동기화(최소 간격 30초, 가정). 동기화 중 행 옆 작은 스피너 "확인 중". 반영되면 해당 행이 **"내가 리뷰함" 그룹으로 이동**, 짧은 토스트 "owner/repo #123: 리뷰를 확인했어요" | 보통 행동 없음. 안 바뀌면 "지금 확인" 버튼 | 이동 시 행 강조 1회(모션 최소, `prefers-reduced-motion` 존중). 요약 줄 숫자 갱신 | ① GitHub 반영 지연으로 아직 대기 ② 내가 리뷰를 안 냈음(보기만 함) ③ 코멘트만 남겨 요청이 안 빠짐(확인 필요) ④ 새 탭에서 돌아왔는데 앱이 갱신 안 함(탭 복귀 이벤트가 안 걸림) | ① "지금 확인" 버튼과 "N초 전 확인" 시각 항상 표시. 3분 폴링이 이어서 잡는다 ② 그대로 대기 유지(정상) ③ 이 경우 "내 리뷰함" 판정은 리뷰 목록 호출 필요(질문 Q5) ④ 수동 버튼이 안전망 |
| 6 | 처리 끝난 것이 정리된다 | "내가 리뷰함": 작성자 응답 대기 중인 PR(접힘). "정리됨": 머지/닫힘/요청 취소 + 이유 + 시각 | 펼쳐서 확인(선택) | 머지되면 행이 "정리됨"으로 이동. 이유 라벨: "머지됨", "닫힘(머지 안 됨)", "리뷰 요청이 취소됨" | ① **내 리뷰 없이 머지됨**: 놓친 건지 알려야 하나, 질책처럼 보이면 안 됨 ② 업그레이드 직후 과거 PR 수십 건이 한꺼번에 정리됨 ③ 정리 항목이 영영 쌓임 ④ 재요청으로 되살아남 | ① 중립 표현 "리뷰 없이 머지됨"(색 경고 없음, 기록 목적) ② 첫 동기화 때 "지난 PR N개를 정리했어요" 한 줄 요약 + 목록은 접힘 ③ 7일 후 사라짐(가정, 질문), "정리됨 전체 보기" 없음(범위 밖) ④ "다시 요청됨" 라벨과 함께 대기로 복귀 |
| 7 | 오늘 끝 | 대기 0건: 짧은 확인 "리뷰 대기 없음" + 프로젝트 흐름 링크 | 닫기 | - | 과한 축하 연출(스트릭/폭죽)은 조작·장식 | 거부. 차분한 한 줄만 |

### 2.4 머지·닫힘·취소 처리 규칙(흐름이 요구하는 시스템 동작)

| 경우 | 사용자에게 | 시스템 요구 |
|---|---|---|
| 내가 리뷰 → 이후 머지 | "정리됨 · 머지됨" | 동기화가 PR `state` 갱신 |
| 내 리뷰 없이 머지 | "정리됨 · 리뷰 없이 머지됨" | 내 리뷰 여부 판단 필요 |
| 머지 없이 닫힘 | "정리됨 · 닫힘" | 위와 동일 |
| 작성자가 내 요청 취소, 리뷰 없음 | "정리됨 · 리뷰 요청이 취소됨" | `requested_reviewers`에서 사라짐을 감지 |
| 재요청 | 대기로 복귀 + "다시 요청됨" | 정리/리뷰함 상태에서도 재평가 |
| 삭제된 PR/레포 접근 불가 | "확인할 수 없음"(J4-E11) | 갱신 실패와 구분 |

수동 삭제·완료 이동은 PR 항목에서 필요 없게 한다(상태가 외부 사실에서 오기 때문). 칸반식 수동 상태 이동은 PR에는 적용하지 않는 것을 제안한다(질문 Q3).

### 2.5 인지 워크스루

| 단계 | ① | ② | ③ | ④ | 메모 |
|---|---|---|---|---|---|
| 1 열기 | ○ | ○ | ○ | △ | 신선도 표시가 없으면 오래된 데이터를 믿는다 |
| 2 훑기 | ○ | ○ | ○ | ○ | 행 정보 과밀 위험. 신호 우선순위 정해야 함(wireframe) |
| 3 우선순위 | △ | △ | △ | ○ | 사용자가 "정렬"로 우선순위를 정한다는 걸 기대하는지 미확인. 사용자 지정 우선순위(핀 등)는 일부러 안 만듦 |
| 4 GitHub 가기 | ○ | ○ | ○ | △ | 앱을 떠남. 돌아와야 한다는 안내 없음 → 복귀 후 단계 5가 설명을 대신 |

핵심 발견: **단계 4→5가 이 흐름의 가장 약한 고리**다. 사용자가 앱 밖에서 행동하고 앱은 그걸 직접 알 수 없다(탭 복귀 + 폴링으로 추정).

### 2.6 사용자 이야기와 끊기는 지점

주인공(가설, 조사 아님): 팀 5명 중 한 명. 오전에 업무 중 슬랙에서 "PR 봐줘"를 받았고, GitHub 알림은 여러 곳에 흩어져 있다.

| 단계 | 감정(가설) | 끊기는 지점 |
|---|---|---|
| 열기 | 약간의 불안(놓친 게 있나) | 신선도 불명확하면 불신. 안정되면 안도 |
| 훑기 | 정리됨, 부담도 보임 | 대기 8건이 한 번에 보이면 압박. 숫자만 객관적으로 |
| 우선순위 | 판단 부담 | 기준이 없으면 "그냥 위에서부터". 괜찮음. 기본 정렬이 결정을 대신 |
| GitHub로 | 몰입 전환 | **이야기가 제품 밖으로 나간다.** 이 단절을 숨기지 않는다 |
| 돌아옴 | 확인 욕구 | **상태가 안 바뀌면 신뢰 붕괴**("앱이 내 리뷰를 모르네"). 지연 설명과 수동 확인 필수 |
| 정리 | 마무리 | 내 리뷰 없이 머지된 항목이 죄책감을 유발하면 안 됨 |

변형(한 호로 합치지 않음): (a) 합류 신규 팀원은 J1 직후 이 흐름에 들어와 맥락이 없다. (b) 리뷰가 몰리는 날은 3단계(우선순위)가 주 과제. (c) 한가한 날은 7단계로 바로 가서 J3으로 간다. 이 셋은 한 이야기로 평균내지 않았다.

### 2.7 측정(가설)
5초 질문 테스트(5명 중 4명), 요청→첫 리뷰 시간(기준선 먼저), 복귀 후 "수동 확인" 클릭 비율(자동 갱신 신뢰 신호; 높으면 단계 5 실패), 단계 5에서 상태 미반영 비율.

## 3. J3 내 일과 무관한 영역의 진행 파악

### 3.1 문제와 성공
- **사용자 목표**: "내가 안 건드리는 부분이 지금 활발한지, 막혔는지, 무엇이 바뀌는지 알고, 그것이 내 작업에 영향을 주는지 판단한다."
- **성공(H2)**: 안 만진 영역 2곳에 대해 **영역당 30초 안에** "활발/막힘/무엇이 바뀜"을 화면만 보고 답한다(정답률 4/5 목표, 가설).
- **정직성 제약**: 보이는 것은 **활동**(커밋·파일 변경)과 **리뷰 대기 PR**이다. "진행률"·"완료율"을 표시하지 않는다(01 §3).

### 3.2 변형

| 축 | 변형 | 차이 |
|---|---|---|
| 목적 | 조망(주 1~2회, 길게) / 특정 영역 확인(내 PR이 걸친 영역) | 후자는 큐의 영역 칩에서 영역 상세로 직행 |
| 레포 수 | 1개 / 여러 개 | 여러 개면 레포 선택 → 영역(`{repoKey}:{groupId}` 접두사, 02 §2-3) |
| 영역 이름 | 폴더명 그대로 / 팀이 붙인 이름 | 이름이 생소하면 이해 실패(G3) |
| 기간 | 기본 30일 | `days` 파라미터 있음. 기간 변경 필요성은 미확인 |

### 3.3 단계표

| # | 사용자 목표 | 화면에 보이는 것 | 행동 | 피드백 | 실패 지점 | 복구 |
|---|---|---|---|---|---|---|
| 1 | 프로젝트 흐름으로 간다 | 내비게이션의 "프로젝트 흐름"(임시 이름). 진입 즉시 개요(S-E) | 클릭 | 스켈레톤(분석 중) → 영역 시각화 | ① 분석이 느림(커밋 분석, 5분 서버 캐시) ② 레포를 직접 입력해야 함(현재 `ArchitectureView`는 URL 수동 입력) | ① "최근 30일 커밋을 분석하는 중" + 캐시 시각 ② **감시 레포 목록에서 선택**(첫 레포 기본). 직접 URL 입력은 없앤다(02 §4-3) |
| 2 | 전체 모양을 한눈에 | 영역별 **주간 활동 스파크라인/막대** 한 줄씩, 추세 라벨(활발해짐/꾸준/조용), 마지막 변경 시점, **리뷰 대기 PR 칩(예 "대기 2 · 최장 5일")**. 정렬: 최근 변경 순. 범례: "활동 = 커밋·파일 변경 기준. 진행률이 아닙니다" | 훑기 | 현재 레포·분석 기간·기준("최근 커밋 60개 기준") 표시 | ① 영역 이름이 폴더명이라 낯섦 ② 한 영역(`Misc`/`Root`)이 비대 ③ 활동이 많다 = 좋다로 오해 ④ 조용함 = 완료로 오해 | ① 이름 바꾸기 진입점(J3-r 참조) ② 비대 영역은 안내 "분류되지 않은 파일이 많아요" ③④ 범례 + "조용함"의 뜻을 툴팁이 아닌 본문 한 줄로 |
| 3 | **막힘 신호를 찾는다** | 개요에서 두 신호의 조합이 눈에 띈다: "조용함 + 대기 PR 있음" = 정체 후보, "활발 + 대기 없음" = 흐름 양호 | 해당 영역 선택 | 선택 시 같은 영역 강조(차트·카드·결합 그래프 연동, 기존 `highlight` 패턴 유지) | ① 신호가 색에만 의존 ② 대기 PR이 PR 목록이 한정(내 리뷰 요청만이 아니라 레포 전체 열린 PR이 필요) | ① 텍스트 라벨 병기 ② **영역 신호는 "리뷰어가 지정된 열린 PR 전체"로 집계해야 함**(내 큐와 다름). 02 §4-1 안 1(`GET /pulls?state=open`)과 같은 수집이면 해결 |
| 4 | 한 영역을 이해한다 | 영역 상세(S-F): 이 영역 이름·종류, 주간 차트, **대기 중인 PR 목록**(제목·작성자·대기 시간·리뷰어), 최근 커밋 몇 건, 최근 변경한 사람, 함께 바뀐 영역(결합) | 목록 읽기, 결합 영역 클릭 | 결합 클릭 시 해당 영역 상세로 이동, 뒤로 가기 가능 | ① 커밋 메시지가 의미 없음("fix") ② 한 PR이 여러 영역에 걸쳐 영역별 합계가 PR 총수와 다름 ③ 내가 영향받는지 판단 불가 | ① 커밋 대신 PR 제목 우선 표시(가능하면) ② "여러 영역에 걸친 PR은 각 영역에 포함"을 표시 ③ 영향 판단은 사람 몫. 앱은 "누가 바꾸는지"를 보여 줘 물어볼 사람을 알려 준다 |
| 5 | 다음 행동을 정한다 | 각 PR·커밋은 GitHub 링크. 작성자 이름 표시 | 클릭 → GitHub 새 탭, 또는 그냥 이해하고 닫음 | - | 앱에서 팀원에게 연락 기능 없음 | 의도적 비포함. 이름을 보여 줄 뿐 |
| 6 | 영역 이름을 정리한다(드문 작업) | 이름 옆 편집 아이콘 → 인라인 입력. 묶기(합치기)는 후속 | 이름 입력 후 확인 | 즉시 반영, 팀 전체 공유 | ① 로컬에만 저장되면 팀원마다 다름 ② 잘못 바꿔도 원복 불가 | ① 서버 저장 필요(00 결정 3, 02 §2-3은 "지금 안 만듦"이라 했으나 결정이 이를 뒤집음 → 백엔드 신규) ② "원래 이름으로 되돌리기" 제공 |

## 4. J4 오류·빈 상태·오프라인·동기화 실패·빈 영역 복구

### 4.1 원칙(모든 상태 공통)

1. **마지막 성공 데이터는 계속 보인다.** 실패가 화면을 비우지 않는다.
2. **"없음"과 "못 가져옴"을 절대 섞지 않는다.** 리뷰 0건(정상)과 동기화 실패는 다른 화면이다. 이것이 정직한 지표 원칙(01 §5)의 UI 버전이다.
3. **신선도는 항상 보인다**: "N분 전 확인". 3분 폴링의 두 배(6분)를 넘으면 "오래됨"으로 한 단계 강조.
4. **오류 문구는 3요소**: 무슨 일이 있었나 / 내게 어떤 영향인가 / 지금 할 일(`/articulate`가 문구 확정). 비난·기술 용어·오류 코드 단독 금지.
5. **그 자리에서 복구**: 흐름을 처음부터 다시 시작시키지 않는다.
6. 낙관적 갱신이 실패하면 **롤백 + 알림**. 현재는 `console.error`만 한다(03 §6.2-5)이므로 구현 계약 변경이 필요하다.

## 5. 흐름이 요구하는 화면별 정보 요구사항 (와이어프레임 입력)

범례: **[있음]** 현재 데이터 존재, **[신규]** 백엔드·API 필요(02 §4), **[결정]** 사용자 결정 대기. 화면 이름은 임시.

### S-A 첫 설정 / 내 로그인 (J1, J4-E5)
- 답하는 질문: 이 앱이 누구의 큐를 보여줘야 하나?
- 필수: GitHub 로그인 입력, 후보 로그인(서버의 `githubLogin`·PR 작성자·커밋 작성자) [있음], 입력 이유 한 줄, 정규화 미리보기, 존재 확인 결과 [신규, 선택]
- 상태: 기본 / 입력 오류 / 후보 없음(J1-a) / 후보 있음(J1-b)
- 행동: 저장(주), 건너뛰기 없음(필수 값). 이후 설정에서 변경
- 이동: 레포 0개면 S-B(레포 추가), 아니면 S-C

### S-B 감시 레포 관리 (J1 단계 2, J4-E4/E6/E12)
- 답하는 질문: 어떤 레포에서 리뷰 요청을 가져오고 있나? 잘 되고 있나?
- 필수: 레포 목록(owner/name, 마지막 동기화 시각, **레포별 상태 성공/실패/동기화 중**) [있음+일부 신규(레포별 오류 상태)], 추가 입력(URL), 삭제, "지금 동기화"
- 상태: 0개 / 추가 중 / 오류 / 중복
- 비고: 현재 레포 단위 `githubLogin` 필드는 사람 설정으로 이동해야 함 [신규, P3]

### S-C 내 리뷰 큐 (J2, 첫 화면)
- 답하는 질문: 지금 내가 리뷰해야 하는 PR은 무엇이고 무엇부터 볼까?
- 상단 요약: 대기 건수, 최장 대기, 마지막 확인 시각 + "지금 확인", 내 로그인 표시
- 그룹: 대기(기본 열림) / 내가 리뷰함(접힘) / 정리됨(접힘, 이유 라벨) / draft(질문 Q4)
- **행 필드**: PR 제목 [있음], 레포·번호 [신규-구조화 필요, 현재 id 문자열 파싱], 작성자 [있음, 구조화 안 됨], 대기 시간 기준 시각(PR `created_at`) [신규], 변경 규모 +/-·파일 수 [신규], 영역 칩 [신규], draft [신규(현재 제목 문자열)], 다른 리뷰어 진행 [신규], 다시 요청됨 [신규], GitHub URL [있음], PR 상태(open/merged/closed) [신규]
- 컨트롤: 정렬(대기 시간/크기/영역), 영역 필터, 행 펼침(상세), 주 행동 "GitHub에서 리뷰"
- 상태: 로딩 스켈레톤 / 대기 있음 / 대기 0(정상, E7) / 0+로그인 의심(E5) / 레포 0(E6) / 동기화 실패 배너(E3,E4) / 오래됨(E13) / 서버 연결 실패(E1)
- 이동: 영역 칩 → S-F, 행 → GitHub 새 탭, 빈 상태 → S-E

### S-D PR 행 펼침 상세 (J2 단계 3)
- 답하는 질문: 이 PR을 먼저 봐야 하나?
- 필수: 변경 영역 목록(영역별 파일 수) [신규], 변경 규모, 리뷰어 목록과 각자 상태 [신규], 작성자·생성 시각·마지막 업데이트 [일부 있음], PR 설명 앞부분 [있음]
- 행동: GitHub에서 열기. 앱 안에서 리뷰·승인·코멘트는 하지 않음(의도적 비포함)

### S-E 프로젝트 흐름 개요 (J3)
- 답하는 질문: 프로젝트의 각 영역이 지금 어떤 모양인가? 어디가 정체 같은가?
- 상단: 레포 선택(감시 레포 기반) [신규 연결], 분석 기간·기준·캐시 시각("최근 30일, 커밋 최대 60개") [있음], 범례("활동이며 진행률이 아님")
- **영역 행 필드**: 영역 이름(표시명/원래 폴더 이름) [있음+결정 3 서버 저장 신규], 종류(`backend/frontend/infra/docs/other`) [있음], 주간 활동 시계열 [있음 `weekly`], 추세 [있음 `trend`], 마지막 변경 [있음 `lastChangeAt`], 최근 변경한 사람 [있음 `authors`], **리뷰 대기 PR 수·최장 대기 시간** [신규], 비대 영역 경고 [신규]
- 보조 시각: 영역 간 결합 그래프 [있음 `couplings`]
- 상태: 로딩 / 정상 / 활동 없음(E9) / 레포 읽기 불가(E9') / 분석 실패(E8) / 영역 사라짐(E10)
- 행동: 영역 선택(강조·상세), 기간 변경(질문), 이름 변경 진입
- 이동: 영역 → S-F

### S-F 영역 상세 (J3 단계 4)
- 답하는 질문: 이 영역에서 무슨 일이 일어나고 있나? 누구에게 물어볼까?
- 필수: 이름, 주간 차트 확대 [있음], **대기 중인 PR 목록**(제목·작성자·대기 시간·리뷰어·GitHub 링크) [신규], 최근 커밋(날짜·작성자·메시지) [있음], 최근 변경한 사람 [있음], 함께 바뀐 영역 [있음], "여러 영역에 걸친 PR 포함" 주석
- 행동: 영역 이름 변경, 결합 영역으로 이동, PR/커밋 GitHub 링크
- 큐 연동: 대기 PR 중 내가 리뷰어인 것에 "내 리뷰 큐에 있음" 표시 [신규 관계]

### S-G 전역 동기화·상태 표시 (모든 화면, J2/J4)
- 필수: 마지막 성공 동기화 시각 [일부 있음 `lastSyncedAt`, 레포별], 현재 동기화 중 여부, 수동 "지금 확인", 오류 배너(요약+원인+행동), 오래됨 임계 상태
- 위치: 큐·개요·상세 모두에서 같은 형태(wayfinding 일관성)

### S-H 설정 (J1, J4-E5)
- 내 로그인 변경, 감시 레포 관리 진입, (후속) 영역 이름 초기화, 테마
- 비포함: 알림 설정, 계정

### 화면 공통 비기능 요구(디자인으로 승계)
접근성(키보드 이동, 포커스 표시, 배너 `role="status"`/오류 `role="alert"`, 색 단독 의존 금지, 본문 12px 미만 금지), 모션 최소(`prefers-reduced-motion`), 용어 통일(03 §2.3 한·영 혼재 해소), 장식 요소 금지(이모지·컬러 그림자·가짜 버전).

## 7. 하지 않기로 한 것

| 안 하는 것 | 이유 |
|---|---|
| 앱 안에서 PR 승인·코멘트 | GitHub이 이미 잘 함. 이 앱의 가치는 앞뒤 흐름 |
| 사용자 지정 우선순위(핀·긴급 표시) | 협업 압박 도구가 됨, 조작 패턴 거부. 정렬만 제공 |
| 리뷰 지연자에 대한 개인별 순위·경고 | 비난 구조. 팀 내 압박 |
| 알림(푸시·메일) | 01 §4 범위 밖 |
| 영역 진행률(%)·완료 표시 | 데이터가 없고 정직하지 않음 |
| 영역 AI 서사 | 01 §3 안 C 제외 |
| 열어본 PR 로컬 표시("방금 연 PR") | 복귀 맥락에 도움이 될 수 있으나 가설 검증 전 추가 안 함. 5단계 실패율이 높으면 재검토 |
| 작성자 관점("내 PR이 누구에게 대기 중") | 핵심 목적에 없음 |
