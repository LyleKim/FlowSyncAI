# 04. 정보 구조(IA) 설계

입력: `00-context.md`(확정 결정 5개), `01-strategy.md`, `02-data-feasibility.md`, `03-current-ui-inventory.md`. 방법론: intent:organize. 코드·사용자 조사는 하지 않았다. **카드 소트·트리 테스트 데이터가 없으므로 모든 구조·라벨은 가설이다.** 시각화(사이트맵 HTML)는 만들지 않았다. 필요하면 요청 시 추가한다. 아래 트리가 그 원본이다.

## 0. 진단 (IA Assessment)

| 현재 | 문제 | 근거 |
|---|---|---|
| 사이드바 4탭: 칸반 / 모든 작업 / 분석 / 아키텍처 | 기능 나열이다. 사용자 질문이 아니라 컴포넌트 이름으로 나뉘었다. 칸반과 목록은 같은 데이터의 두 보기다. | `Sidebar.tsx`, 03 §1.1 |
| 첫 화면 = 칸반(항상 `board`) | "내가 지금 처리할 것"이 첫 화면에 없다. "나" 개념이 없다. | 03 §1.1, 00 P0 |
| 칸반 안의 2단계(상태 포털 → 카드 그리드) | 진짜 칸반이 아니고, 한 번 더 클릭해야 내용이 보인다. | 03 `TaskBoard.tsx:177-228` |
| URL 없음 | 뒤로가기·링크 공유·새로고침 복원 불가. wayfinding 4질문 중 "어디 있나"와 "돌아갈 수 있나"가 깨진다. | 03 §1.1 |
| 감시 레포·테마가 헤더 아이콘에 흩어짐 | 설정이 한 곳에 없다. 아이콘만 있고 `aria-label`이 없다. | 03 §5.2 |
| 같은 개념에 다른 이름 | 용어 혼재(§2). | 00 P2 |

IA 원칙(01 §5 승계): 화면마다 "이 화면이 답하는 질문"을 한 문장으로 말할 수 있어야 한다. 이 질문에 답하지 못하면 1급 메뉴가 될 수 없다.

## 1. 최상위 내비게이션 (추천안)

모드 기준(페르소나 아님): 사용 리듬이 다른 두 질문(하루 여러 번 짧게 / 주 몇 번 길게)을 별도 진입점으로 분리한다(01 Q3).

| 순서 | 라벨(제안) | 이 화면이 답하는 질문 | 주 사용 리듬 | 기반 |
|---|---|---|---|---|
| 1 (기본) | **내 리뷰 요청** | 지금 내가 리뷰해야 할 PR이 무엇이고, 가장 오래 기다린 건 어느 것인가? | 하루 여러 번 | PR 동기화 Task, 로컬 `githubLogin` |
| 2 | **영역 흐름** | 내가 만지지 않는 영역에서 최근 무슨 일이 일어나고, 어디가 막혀 있나? | 주 몇 번 | 아키텍처 그룹(승격) + 영역별 리뷰 대기 PR |
| 3 | **전체 작업** | 팀에 어떤 작업이 있고 각각 어떤 상태인가? (검색/필터) | 필요할 때 | 칸반+목록 통합 |
| 4 (하단 고정) | **설정** | 나는 누구이고, 어떤 레포를 추적하며, 영역 이름은 무엇인가? | 처음·가끔 | 로컬 로그인, 감시 레포, 영역 별칭, 테마 |

항목 수 4개: 플랫(flat) 패턴이 맞다. 7~10개 한계 안이고 서로 우선순위가 다른 최상위 모드이므로 계층이 필요 없다. 각 항목 안의 로컬 내비게이션은 필터/보기 전환 정도로 제한한다.

라벨 검증(가설):
- 사용자의 말 "내 리뷰 요청"을 그대로 쓴다. 목적지를 말한다(포맷 라벨 "Hub/Library" 회피).
- "영역 흐름"은 사용자가 쓴 "영역"에 "흐름"(기존 아키텍처 페이지의 "변경 흐름")을 붙인 것이다. 01 §3에 따라 "진행"이라 부르지 않는다(활동량 ≠ 진행).
- 사용자 예시 "내 할 일 / 팀 흐름"과의 차이: "내 할 일"은 수동 태스크까지 포함하는 듯 읽혀 범위가 넓어진다. 이번 범위는 PR 리뷰 큐다. 이 선택은 §5 질문 1.
- 5초 테스트(예정): 라벨 4개만 보여주고 "내가 리뷰할 PR은 어디에 있을까요?"를 물어 첫 클릭이 1번인지 본다.

### 사이트맵

```
FlowSyncAI
├─ 내 리뷰 요청 (기본)            /me
│   ├─ 리뷰 대기 (대기 시간 순)
│   ├─ 리뷰 완료·닫힘 (접힘)
│   └─ → PR 상세 패널              /tasks/:id
├─ 영역 흐름                      /areas
│   ├─ 전체 영역 개요 (활동 흐름 + 리뷰 대기 신호)
│   └─ 영역 상세                   /areas/:areaId
│       ├─ 최근 활동 (주간 흐름, 기여자, 마지막 변경)
│       ├─ 이 영역의 리뷰 대기 PR  → PR 상세 패널
│       └─ 함께 바뀐 영역 (결합)   → 다른 영역 상세
├─ 전체 작업                      /tasks
│   ├─ 보기: 보드 | 목록 (한 화면, 전환 토글)
│   ├─ 필터: 상태, 담당자, 영역, 종류(PR/수동)
│   └─ → 작업 상세 패널            /tasks/:id
└─ 설정                           /settings
    ├─ 나 (GitHub 로그인)
    ├─ 연결된 레포 (추가/삭제/지금 동기화)
    ├─ 영역 이름 (별칭·묶기)
    └─ 화면 (테마)
전역: 검색(제목·영역·작성자), 새 작업, 동기화 상태
```

## 4. 이동 구조와 첫 화면

### 첫 화면 규칙

앱을 열면 **내 리뷰 요청**이 먼저 보인다. 단, 상태에 따라 분기한다.

| 상태 | 첫 화면 | 이유 |
|---|---|---|
| 내 GitHub 로그인 미설정 | "나" 선택 안내(입력 + 후보 칩: 연결된 레포 로그인, PR 작성자, 기여자) → 저장 후 내 리뷰 요청 | 결정 1. 이 단계 없이 큐가 성립하지 않는다 |
| 로그인 있음, 연결된 레포 없음 | 내 리뷰 요청의 빈 상태 → "연결된 레포 추가"(설정으로) | 빈 상태는 "왜 비었고 무엇을 하나"에 답한다 |
| 정상 | 내 리뷰 요청: 대기 시간 순 | H1 성공 신호: 5초 안에 "내 대기 PR 수"를 답함 |
| 내 대기 0건 | "리뷰할 요청이 없어요" + **영역 흐름 보기** 링크 | 큐가 비었을 때 목적 2로 자연스럽게 이어짐 |
| 마지막으로 본 화면 복원 | **하지 않는다** | 첫 화면의 고정이 H1 검증 조건. URL이 생기므로 직접 링크는 가능 |

### 화면 간 이동

- **전역**: 좌측 내비 4개(항상 보임, 현재 위치 표시) + 상단에 동기화 상태 한 줄("3분 전 가져옴"). 브라우저 뒤로가기가 동작하도록 라우터 도입(대규모 변경 표시 §6).
- **크로스 링크(폴리하이어라키는 링크로만, 복제 금지)**:
  - 리뷰 요청 → 그 PR이 건드린 영역 칩 → 영역 상세
  - 영역 상세 → "이 영역의 리뷰 대기 PR" → 작업 상세 패널
  - 영역 개요의 정체 신호 "리뷰 대기 N건" → 전체 작업(영역 필터 적용)
  - 영역 상세 → 함께 바뀐 영역 → 다른 영역 상세
- **작업 상세**: 모달이 아니라 오른쪽 패널(+ URL `/tasks/:id`). 닫으면 원래 목록 위치·필터가 유지되어야 한다(모달 안에서 상태 바꾸면 보드 첫 화면으로 튕기는 현재 동작 폐기, 03 §1.2).
- **wayfinding 4질문**: 어디 있나(활성 항목+페이지 제목+영역 상세 브레드크럼) / 어디 갈 수 있나(4항목+크로스 링크) / 맞게 왔나(제목이 질문과 일치) / 도착했나(내 리뷰 요청의 첫 줄이 "대기 N건").
- 모바일: 03 §1.1대로 현재 반응형이 없다. 이번 IA는 데스크톱 우선, 4항목이므로 후속에 하단 탭 4개로 옮기기 쉬운 구조다(미설계).

## 5. 대안과 트레이드오프

| | **A. 4개 플랫 내비 (추천)** | B. 단일 홈 대시보드 | C. 2개 내비 + 전체 작업 흡수 |
|---|---|---|---|
| 구조 | 내 리뷰 요청 / 영역 흐름 / 전체 작업 / 설정 | 홈 한 화면에 "내 리뷰"(좌)와 "영역 개요"(우). 나머지는 보조 | 내 리뷰 요청 / 영역 흐름. 전체 작업은 영역 흐름 하위 탭, 설정은 헤더 |
| 장점 | 질문 하나에 화면 하나. 사용 리듬이 다른 두 목적이 안 섞임. 후속 기능(작성자 화면 등) 추가가 쉽다 | 한 번 열면 두 목적이 다 보임. 클릭 최소 | 최소 구조. 목적 2개에 집중 |
| 단점 | 항목 하나 더. 전체 작업의 위상이 모호할 수 있음 | 화면 두 개 일을 한 화면에 몰아 위계 흐려짐(01: 리듬이 다름). 영역 시각화가 작아져 "시각화 필수" 약화 | "전체 작업"이 영역의 하위라는 가정이 어색. 수동 작업·상태 보드의 집이 불분명, 설정 발견성 낮음 |
| 위험 | 낮음 | 중: 반응형이 없어서 좁은 화면에서 깨짐(추측) | 중: 질문 2 결과(수동 작업 존속)에 따라 구조가 틀어짐 |
| 확장 | 좋음 | 보통 | 낮음 |

**추천: A.** 이유: (1) 01 Q3의 두 목적이 사용 리듬이 다르다. (2) 각 항목이 질문 하나에 답한다. (3) "전체 작업"은 수동 작업과 상태 보드의 집이라 질문 2의 결과가 어느 쪽이든 안전하다(축소되면 B/C 방향으로 후퇴 가능). B는 좋은 후속 실험 후보: 내 리뷰 요청 상단에 영역 요약 한 줄 정도만 얹는 선에서 A를 보강할 수 있다.

만들지 않기로 한 것: 활동 피드 메뉴, 분석/통계 메뉴, 사용자(팀원)별 화면, 작성자 관점("내 PR의 리뷰 상태") 화면, 전역 검색 통합(후속), 모바일 전용 내비.

## 7. 사용자 확인이 필요한 결정

1. **첫 내비 이름과 범위**: "내 리뷰 요청"(PR만)으로 갈까, 사용자 예시처럼 "내 할 일"(PR + 나에게 지정된 수동 작업)로 넓힐까? 추천은 "내 리뷰 요청". 수동 작업은 전체 작업에서 "담당자: 나"로 거른다.
2. **수동 작업·서브태스크·역할 검토·AI 체크리스트의 위상**: 이 IA는 "보조(상세 패널 접힘)"로 전제했다. 팀이 실제로 쓰는지(01 A7)에 따라 전체 작업과 "새 작업" 버튼의 존속 여부가 달라진다.
3. **대기 시간 기준**: PR 생성 시각으로 충분한가, 리뷰 요청 시각이 꼭 필요한가(02 질문 2)? 라벨은 어느 쪽이든 "대기"로 쓰되, 정확도가 다르다.
4. **영역 이름**: 폴더명 그대로 시작해도 되는가? 별칭을 팀원 간 공유해야 하면 서버 저장이 필요하다(범위 확장). 기본은 로컬 저장 + 공유 안 됨.
5. **용어 변경 승인**: 특히 "감시 레포 → 연결된 레포", "아키텍처 → 영역 흐름", "카테고리 → 분류", "리뷰"(GitHub)와 "역할 검토"(앱 내) 분리.
6. **내 큐가 비었을 때 보여줄 것**: "영역 흐름 보기" 링크만으로 충분한가, 영역 요약을 직접 얹을까(대안 B 방향)?
7. **라우터·App 분해를 이번 리디자인 범위에 넣을 것인가**: 넣지 않으면 URL·뒤로가기·패널 구조가 불가능하다. 이 IA는 라우터 도입을 전제로 한다.
