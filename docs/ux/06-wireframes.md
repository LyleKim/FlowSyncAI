# 06. 화면 구조 설계 (Wireframes)

입력: 00~05. 방법론: Intent `/wireframe`. 산출물: 이 문서 + `docs/ux/wireframes/index.html`(단일 파일, 외부 의존성 없음, Grid / Slides / Prototype 보기, 라이트·다크).

**이 산출물의 층위**: 전체 화면 와이어프레임(mid-fi)과 클릭 프로토타입이다. 아이디어 비교(thumbnail)는 하지 않았다. 구조는 04·05에서 이미 정해졌고 이번 질문은 "화면에 빠진 것이 없는가, 무게가 맞는가"이기 때문이다. **구조에 대해 피드백해 달라. 글꼴·색·간격 같은 시각 디자인은 일부러 없다**(Impeccable 단계). 모든 문구는 정직한 가안이라 `/articulate`가 확정한다.

**근거 강도**: 사용자 조사 0건. 모든 구조는 가설이다. 와이어프레임의 샘플 데이터(PR 제목, 사람, 숫자)는 이 저장소의 실제 모듈 이름을 빌린 **가상 데이터**다.

**HTML 구현 메모**: Intent 키트(CSS/JS)를 그대로 넣었으나 주석만 줄였다(규칙·로직 동일). 보기 → 파일 열기 → Prototype 탭에서 사이드 메뉴·영역 칩·"대기 N건"·"영역 이름 정리" 등 실제 요소를 누른다. 접힘/펼침, 상세 패널 열기/닫기, 목록↔보드는 와이어프레임 내부에서 동작한다. 사이드바는 JS 한 곳에서 생성한다(프레임마다 같은 내비가 어긋나지 않게).

## 2. S-A 첫 설정 (프레임 1)

**답하는 질문**: 이 앱이 누구의 큐를 보여줘야 하나?
**위계**: ① 제목(질문형) → ② 입력 이유 한 줄 → ③ 로그인 입력(큰 컨트롤) → ④ 후보 칩 → ⑤ 주 버튼 하나.

| 요소 | 이유(원칙) |
|---|---|
| 입력 이유를 폼 위에 말한다 | 05 J1 워크스루: 가치 전에 입력부터 요구하면 이탈. 심리적 안전: 왜 묻는지·어디에 저장되는지(이 브라우저에만) |
| "팀이 이미 레포 2개를 연결해 두었어요" 콜아웃 | J1-b(합류자): 레포 추가 단계를 건너뛴다는 걸 알려 단계 수를 줄인다 |
| 정규화 미리보기("minji-park 으로 확인해요") | 오류 예방 > 오류 복구. 대소문자 오타를 입력 중 해결 |
| 후보 칩 | 서버가 이미 아는 로그인만(오타 감소). 후보가 없으면(J1-a) 영역이 사라지고 레포 추가가 다음 단계 |
| 주 버튼 라벨 "저장하고 내 리뷰 요청 보기" | 동사 + 결과. "다음"·"확인" 금지 |
| 사이드바 없음 | "나"가 없으면 큐가 성립하지 않으므로 다른 메뉴로 도망갈 길을 두지 않는다(건너뛰기 없음, 05 §5 S-A) |

**상태**: 기본(프레임 1) / 입력 오류(입력창 `error` + 인라인 `field-error`, 값 유지: "GitHub 로그인에는 공백이나 @를 쓸 수 없어요") / 후보 없음(J1-a: 칩 영역 제거, 저장 후 설정의 레포 추가로 이동) / 후보 있음(J1-b, 프레임 1).
**키보드·스크린리더**: 입력은 `label`로 연결, 힌트와 미리보기는 `aria-describedby`. 칩 그룹은 `role=group` + 라벨. 페이지 로드 시 입력에 포커스. 저장은 Enter로도 가능(폼 제출).
**반응형**: 단일 열이라 그대로 축소(카드 폭만 줄어듦).

## 3. S-C 내 리뷰 요청 (프레임 2~6)

**답하는 질문**: 지금 내가 리뷰해야 하는 PR은 무엇이고 무엇부터 볼까?
**위계(5초 스캔 순서)**: ① 요약 숫자 "대기 4건 / 가장 오래 4일"(가장 큰 글씨) → ② 마지막 확인 시각(제목 줄) → ③ 정렬·필터 → ④ 대기 목록 → ⑤ 접힌 그룹 2개(내가 리뷰함, 정리됨).

### 3.1 한 행의 구조

| 위치 | 내용 | 이유 |
|---|---|---|
| 좌: 대기 열 | "대기 4일"(굵게), 보조 "PR 생성 기준", "다시 요청됨" 배지 | 정렬 기준이자 H1의 핵심 신호를 가장 왼쪽(읽기 시작점)에 둔다. 기준 표기는 Q9(생성 시각 vs 요청 시각) 미결이라 솔직하게 |
| 중: 제목 | PR 제목(`h3`), 메타(레포 #번호, 작성자, +추가 −삭제 · 파일 수, 다른 리뷰어 진행), 영역 칩 | 결정에 필요한 신호만. 대기 → 크기 → 영역 → 다른 리뷰어 순서 |
| 우: 행동 | `GitHub에서 리뷰`(보조 버튼), 펼침 토글(아이콘 버튼) | 05 J2: 앱 안 승인·코멘트 없음. 반복되는 행 버튼은 보조 스타일로 두고 **채움(주) 버튼은 화면에서 펼친 행의 하나뿐** — 8행이 모두 주 버튼이면 위계가 없다 |

- 영역 칩 최대 2개 + "외 N". 칩은 `영역 상세`로 가는 실제 버튼.
- 값이 없으면 "알 수 없음"(프레임 2의 #64, 변경 규모·영역). 0으로 위장하지 않는다(01 정직한 지표).
- 대기 시간은 숫자와 굵기로만 표시한다. 빨강·불꽃·경고 아이콘 없음(조작적 압박 거부, 05 §2).
- 펼침(S-D): 바뀐 영역(영역별 파일 수 표) · 리뷰어와 각자 상태 · 작성자 설명 앞부분 · 생성/업데이트 시각 · 주 버튼 `GitHub에서 리뷰` + "리뷰는 GitHub에서 남겨요. 돌아오면 이 목록이 알아서 갱신돼요."(05 J2 4→5단계의 가장 약한 고리를 문장으로 메운다).

### 3.3 상태 변형

| 상태 | 구조 | 프레임 |
|---|---|---|
| 로딩(첫 가져오기) | 제목 줄에 스피너+"확인 중…"(라벨이 상태를 말함), 레포별 진행 카드(✓ 완료·건수 / 확인 중), 아래 스켈레톤 행 3개. 10초 넘으면 문구가 "계속 확인하는 중이에요. 다른 화면으로 가도 돼요"로 바뀜 | 3 |
| 정상 | 프레임 2 | 2 |
| 일부 레포 실패(E4) + 오래됨(E13) | 목록 **위** 상시 오류 배너(`role=alert`): 어떤 레포·영향·할 일("이 레포만 다시 시도", "연결된 레포 상태 보기"). 요약 라벨에 "(확인된 레포 기준)". 신선도는 굵게+"14:02 기준"(6분 초과 시). 실패 레포의 행은 직전 데이터 유지 + "확인 안 됨" 배지 | 4 |
| 전체 실패(E3) | 위 배너가 "GitHub에서 리뷰 요청을 가져오지 못했어요. 아래는 14:02 기준이에요"로, 원인별 한 줄(토큰 오류 / 호출 한도: 재시도 버튼 비활성+가능 시각 / GitHub 장애). 이전 목록은 유지 | 문서만 |
| 서버 연결 실패(E1) | 첫 로드면 본문 전체 오류("서버에 연결할 수 없어요" + 다시 시도, 자동 재시도). 세션 중이면 상단 배너 + 화면 유지 | 문서만 |
| 대기 0건(E7) | 요약 카드: "지금 리뷰 대기 요청이 없어요 / 레포 2개에서 minji-park 에게 온 요청을 확인했어요" + 아래 **영역 요약 3줄**(S-E와 같은 표 재사용) + "영역 흐름 전체 보기". 축하 연출 없음 | 5 |
| 0건 + 로그인 의심(E5) | 위 카드 문구가 "N개 레포에서 {login}에게 온 리뷰 요청이 없어요. 로그인이 맞는지 확인해 보세요" + 설정 링크로 바뀜(정상 0건과 구분) | 문서만 |
| 레포 0개(E6) | 첫 사용형 빈 상태: "아직 리뷰 요청을 가져올 레포가 없어요" + 주 버튼 `레포 추가`(설정으로) | 문서만 |

**없음과 못 가져옴을 한 화면에서 섞지 않는다**(05 J4 원칙 2). 프레임 4의 배너 + 프레임 5의 확인 문구가 그 대비다.

### 3.4 반응형 (프레임 6, 390)

- 사이드바 → 하단 탭 4개(`tabbar`). 행은 세로로 쌓이고, 대기 열이 제목 위로 올라온다. 펼침 상세·정렬·필터는 이번 범위에서 생략(읽기·바로가기 용도, 05 J2 "모바일은 읽기 전용 확인 정도"는 **추측** — 사용 맥락 미확인).
- 태블릿(768): 사이드바를 아이콘 폭으로 접고(라벨은 `aria-label`), 행의 우측 행동 버튼은 아래 줄로 내린다(미도식).
- 터치 타겟은 키트 최소 32 이상, 주 행동 버튼은 모바일에서 전체 너비.

### 3.5 키보드·스크린리더
- 행은 `ul > li`, 제목이 `h3`라 헤딩 탐색이 가능. 그룹 헤더는 `button` + `aria-expanded` + `aria-controls`.
- 펼침 토글은 아이콘 버튼이며 `aria-label="#58 자세히 보기"`처럼 대상을 말한다.
- 대기 시간·변경 규모는 텍스트라 색 없이 읽힌다. 정렬이 바뀌면 `role=status` 영역에서 "대기 오래된 순으로 정렬했어요"를 알린다.
- 동기화로 행이 "내가 리뷰함"으로 이동하면 토스트(`role=status`)로 알리되, 포커스는 옮기지 않는다. 사라지는 토스트에만 의존하지 않고 그룹 건수도 갱신된다.
- `prefers-reduced-motion`이면 이동 강조를 생략.

## 4. S-E 영역 흐름 개요 (프레임 7, 9) — 시각화 명세

**답하는 질문**: 프로젝트의 각 영역이 지금 어떤 모양이고 어디가 정체 같은가?
**위계**: ① 제목 + 레포·기간 선택 → ② **"활동이에요. 진행률이 아니에요."** 콜아웃(분석 한도·시각 포함) → ③ 범례 → ④ 영역 표(시각화의 본체) → ⑤ 함께 바뀐 영역(보조).

### 4.1 형태 선택과 이유

전략 안 A(활동)에 2단계 신호(리뷰 대기)를 얹는다(결정 5). 형태는 **영역당 한 행인 작은 다중 차트(small multiples) 표**다. 후보와 비교:

| 후보 | 장점 | 버린 이유 |
|---|---|---|
| 겹쳐 쌓은 주간 막대 1개(현재 `WeeklyChart`) | 한 그림 | 영역 7~10개가 쌓이면 서로 읽히지 않고 색 범례에 의존(색 의미 충돌, 03 §2.1) |
| 타일/히트맵 격자 | 한눈에 | 영역 이름과 "대기 PR" 같은 보조 정보를 붙일 자리가 없음. 눈금 해석이 어려움 |
| **한 행 = 한 영역 표(채택)** | 같은 눈금으로 비교, 이름·추세·대기를 같은 행에서 읽음(정체 신호의 전제), 네이티브 `table`이라 접근성 확보 | 영역이 20개 넘으면 길어짐 → 정렬·필터로 대응(미도식) |

### 4.2 데이터 → 마크 매핑

| 데이터(필드, 02/타입 근거) | 마크 | 인코딩 규칙 |
|---|---|---|
| `weekly[].commits` (주별 커밋 수) | **세로 막대 5개**(주당 1개) | 막대 **높이** = 커밋 수. 1칸 = 커밋 2개, 최대 8칸(16개)에서 **모든 영역이 같은 눈금**(영역 간 비교 가능). 16 초과는 최대 칸에서 자르고 영역 상세에서 숫자로 확인 |
| 주 순서 | 가로축 | **왼쪽 = 가장 오래된 주, 오른쪽 = 이번 주**. 모든 행 동일. 범례에 문장으로 명시. 눈금 숫자는 행마다 반복하지 않음(범례 1회 + 상세에서 숫자) |
| 이번 주(마지막 `weekly`, 진행 중) | 속이 빈 막대(테두리만) | 주가 끝나지 않아 다른 주와 비교하면 오해(작아 보임)하므로 **다른 마크**로 구분. 범례에 설명 |
| 0 커밋 | 막대 없음, 바닥선만 | "0"은 "활동 없음"이라는 **측정된 값** |
| 데이터 없음/알 수 없음 | **점선 짧은 막대**(프레임 9의 연결 끊김 행) | 0과 모름을 구분. 이름이 가리키던 경로가 사라진 경우 등 |
| `trend` (rising/steady/quiet) | **글자**: 활발해짐 / 꾸준함 / 조용함 | 색·아이콘 없이 단어만. 막대 모양이 이미 말하고 있어 글자는 확인용 |
| `lastChangeAt` | "오늘 / 어제 / N일 전", 분석 기간 밖이면 "41일 전 (30일 밖)" | 상대 시각. 절대 날짜는 `title`/영역 상세에 |
| 영역 대기 PR 수(신규) | 텍스트 링크 "대기 3건" | 클릭하면 전체 작업(영역 필터 적용) |
| 영역 최장 대기(신규) | 짧은 **가로 막대**: 길이 = 일수(1칸 = 1일, 7일 이상은 7칸에서 자르고 "7일+"로 적음) + 글자 "최장 4일" | 막대는 대기 영역끼리 비교용, 글자는 정확한 값 |
| 정체 후보 | 반전 배지 "정체 후보" + 경고 글리프 + 한 줄 설명 | **규칙: `trend = quiet` 그리고 대기 ≥ 1건**(임시, 열린 질문). 색이 아니라 글자+기호 |
| `authors`, `fileCount`, 경로 | 이름 아래 보조 줄(작은 글자) | 영역 이름 → 원래 경로 순서로 두 겹으로 보여 줘 별칭이 있어도 원래 위치를 잃지 않게 |
| 비대 영역(`Misc`/기타) | 이름 아래 경고 글리프 + "분류되지 않은 파일이 많아요(약 38%)" | 영역이 잘 안 나뉘었다는 사실을 숨기지 않는다 |

색은 쓰지 않는다(와이어프레임은 회색조). 구현 단계에서 색을 더하더라도 **의미(상태·강조) 하나에만** 쓰고 영역마다 다른 색을 주지 않는다 — 영역 식별은 색이 아니라 이름이다(03 §2.1 색 의미 충돌 반면교사).

### 4.3 정렬·빈 값·한도

- **정렬** 기본: 최근 변경 순. 선택지: 리뷰 대기 많은 순 / 이름. 정체 후보를 맨 위로 올리는 정렬은 만들지 않는다(주의를 강요하지 않기).
- **빈 값**: 5가지를 시각·문구로 구분한다. 0(바닥선) / 모름(점선) / 분석 기간 밖 마지막 변경(문구) / 대기 없음(회색 글자) / 연결 끊김(배지).
- **한도의 정직성**: 분석은 최근 커밋 최대 60개(`truncated` 플래그, `activity.py:9`). 잘렸으면 콜아웃에 "최근 60개만 분석했어요(가장 오래된 주는 일부만 반영)" — 조용함이 "분석 한도" 때문일 가능성을 밝힌다. `analyzedCommits`·`generatedAt`을 콜아웃에 쓴다.
- **눈금 가정**: `weekly`의 개수는 `days`에서 파생(30일≈5주)으로 가정했다 — **확인 필요**. 기간을 90일로 늘리면 막대가 13개가 되어 막대 폭이 줄고, 이 경우 지금 폭 대신 영역 열을 넓히는 쪽을 택한다(미도식).
- **함께 바뀐 영역**(`couplings`)은 원형 그래프 대신 **순위 목록 + 가로 막대(함께 바뀐 커밋 수)**로 단순화했다. 이유: 원형 노드 그래프는 접근성과 이름 길이에 취약하고 목록이 같은 정보를 더 정확히 말한다(기존 구현의 키보드 지원은 있으나 유지 비용 대비 이득이 약하다고 판단 — **사용자 확인 필요**, §7 질문 2).

### 4.5 키보드·스크린리더
- 네이티브 `table` + `caption`(숨김) + `th scope=col`. 영역 이름은 행의 주 링크(`button`).
- 막대 묶음은 `role=img` + `aria-label`("5주 커밋: 4, 6, 10, 14, 16개(마지막은 진행 중인 주)") — 시각 마크의 모든 숫자가 텍스트로도 존재.
- "정체 후보"는 글자라 그대로 읽힌다. 가로 막대(대기)는 장식이고 같은 값이 글자("최장 4일")로 있다.
- 범례는 본문 텍스트(툴팁이 아님). "조용함"의 뜻은 콜아웃 본문 한 줄(05 3.3-2).
- 선택(강조)이 필요한 상호작용(예: 행 호버로 결합 목록 강조)은 만들지 않았다 — 키보드로 같은 효과를 내기 어렵다. 필요하면 후속.

### 4.6 반응형
- 1440: 5열 표 그대로. 1024: "추세"와 "마지막 변경"을 한 열로 합침. 768 이하: 행이 카드로 바뀜(이름·막대·"대기 N건"만 위 줄, 나머지는 아래 줄). 막대 눈금은 반응형에서도 유지(크기 줄이지 않고 줄바꿈).

## 5. S-F 영역 상세 (프레임 8)

**답하는 질문**: 이 영역에서 무슨 일이 일어나고 있나? 누구에게 물어볼까?
**위계**: ① 영역 이름(+ 원래 경로·추세·마지막 변경) → ② 주간 활동(개요와 같은 마크, 값 숫자 표기) → ③ **리뷰 대기 PR 표**(막힘이 이 화면의 핵심 질문) → ④ 최근 커밋 → (우측) 최근 변경한 사람 / 함께 바뀐 영역 / 포함 경로.

| 요소 | 이유 |
|---|---|
| 막대 위 값, 아래 주 시작일 | 개요에서는 마크만, 상세에서는 정확한 값 — 두 단계(개요→상세) 공개. 툴팁 의존 금지 |
| 대기 PR 표(PR, 작성자, 대기, 리뷰어, GitHub 링크) | 05 J3-4. "내 리뷰 요청에 있음" 배지로 큐와 연결(S-F 큐 연동). 여러 영역에 걸친 PR은 각 영역에 포함된다는 주석 |
| 최근 커밋은 PR 제목 우선이 이상적 | "fix" 같은 메시지 문제(05 J3-4 ①). 이 와이어프레임은 커밋 메시지를 썼지만 PR 제목 우선 표시를 `/articulate`와 정함 |
| "최근 변경한 사람" 아래 "물어볼 사람을 찾는 용도예요. 순위나 평가가 아니에요." | 개인 순위 거부(05 §7). 정렬은 최근 변경 순이며 숫자 순위를 표시하지 않음 |
| 이름 바꾸기 | 여기서도 열 수 있다(이름이 낯설다고 느끼는 바로 그 자리). 편집은 인라인 입력 + 저장/취소(미도식), 변경은 팀에 공유됨을 고지 |
| 뒤로 `영역 흐름` 버튼 | 브레드크럼 대신 한 단계 깊이라 뒤로 버튼이면 충분. 브라우저 뒤로가기도 동작(라우터) |

**상태**: 로딩(스켈레톤) / 정상 / 대기 PR 0건("지금 리뷰 대기 PR이 없어요" — 사라진 영역이 아님을 분명히) / 활동 0(막대 없음 + 문구) / 영역이 사라짐(E10: 상세 URL 접근 시 "이 영역은 더 이상 코드에서 보이지 않아요" + 영역 흐름으로).
**키보드**: 대기 PR 표의 GitHub 링크는 행마다 `aria-label="#58 GitHub에서 열기"`로 구분. 함께 바뀐 영역은 `list-row` 버튼.
**반응형**: 768 이하에서 우측 열이 아래로 내려오고 순서는 사람 → 결합 → 경로.

| 연결된 레포 | 레포별 행: 이름, 마지막 확인, 상태 배지(정상/실패) + 실패 사유 글자(색 단독 의존 금지), 연결 해제 / 다시 시도. 아래 레포 추가 입력. "지금 가져오기"가 제목 줄 우측 — 큐의 실패 배너가 가리키는 도착지. 연결 해제 시 확인 대화상자("연결을 해제하면 이 레포의 리뷰 요청이 내 리뷰 요청에서 사라져요", 버튼 "연결 해제")는 미도식 |

| 화면 | 라디오 3개(시스템/밝게/어둡게). 현재 `.dark` 클래스와 `dark:` 변형이 맞지 않을 가능성(03 §3)은 구현 단계 과제 |

**상태**: 레포 0개(빈 상태 + 입력 강조) / 추가 중(버튼 안 스피너 "추가하는 중…") / URL 형식 오류(인라인) / 중복 409("이미 연결된 레포예요" — 오류가 아니라 안내) / 비공개·권한 없음(사유 문구) / 서버 저장 실패(해당 줄 인라인, 입력값 유지).
**접근성**: 모든 입력에 `label`(표 안 입력은 `aria-label`로 경로를 포함), 라디오는 `radiogroup`. 저장 결과는 `role=status`.
**반응형**: 단일 열이라 그대로. 표는 768 이하에서 행 카드(경로 위, 입력 아래).

## 8. 접근성 공통

- 포커스 링은 키트의 2px 강조 링을 모든 컨트롤에 유지, `outline:none` 금지(03 §5.2: 18곳).
- 본문은 12px 미만 없음(키트 하한 11px은 캡션·메타에만 쓰고 핵심 정보 — 대기 시간·상태·건수 — 는 13px 이상. 구현 단계에서 캡션도 12px로 올릴지 `/include`와 결정).
- 색에 의존하는 신호 없음: 정체 후보, 연결 끊김, 실패, 이번 주 막대 모두 글자·모양으로도 구분.
- 오류는 `role=alert`, 신선도·정렬 결과는 `role=status`. 모달은 쓰지 않고 패널/인라인(대화상자는 연결 해제 확인 한 곳).
- 읽기 순서 = 시각 순서 = DOM 순서(제목 → 요약 → 컨트롤 → 목록). 각 프레임은 `h1` 하나. 건너뛰기 링크(`본문으로 건너뛰기`)를 사이드바 앞에 둔다(미도식).
- `lang="ko"`로 설정(03 §5.2 `lang="en"` 오류 수정).
