# FlowSyncAI UX 전략 브리프

작성 기준: `docs/ux/00-context.md`, `README.md`, `docs/DECISIONS.md`, 그리고 코드 리딩(아래 근거 표기). **사용자 조사는 한 건도 없다.** 이 문서의 "증거"는 모두 (a) 사용자가 직접 말한 목적, (b) 코드·문서 읽기다. 인터뷰·로그·사용 데이터는 없으므로 대부분의 판단은 가설이다.

증거 강도 표기: **[강]** 3개 이상 독립 출처로 삼각검증 / **[중]** 2개 출처 또는 한 출처 내 다수 / **[약]** 단일 출처·추측. 지금은 사용자 진술(1인)과 코드 리딩뿐이라 **[강]은 없다.** 정직하게 [중]이 최대다.

---

## 0. 상황 → 긴장 → 제안 (요약)

- **상황**: 2~10명 팀이 각자 PR을 올리고 서로 리뷰한다. 이미 감시 레포 + 리뷰 요청 PR 자동 할 일 생성이 있고(`backend/integrations/pr_sync.py`), 레포 변경을 코드 그룹별로 보여주는 아키텍처 페이지가 있다.
- **긴장**: README의 원래 문제는 "소통 부족으로 불필요한 작업이 생긴다"(`README.md:9-12`)였다. 그런데 현재 제품은 "내 리뷰 요청"도, "내가 안 건드리는 영역의 흐름"도 한 화면에서 답하지 못한다. 칸반/리스트/분석/활동 피드는 그 두 질문 어디에도 직접 답하지 않는다.
- **제안**: 제품을 "내가 지금 처리할 것(리뷰 큐)"과 "프로젝트 다른 영역이 어떻게 흘러가는가(영역 흐름)" 두 질문에 맞춰 재구성한다. 나머지는 이 둘을 돕는 도구로 강등하거나 폐기한다.

주의(허위 정렬 방지): 위 "긴장"은 사용자 진술과 코드 구조에서 도출한 것이지, 실제 팀원이 겪는 빈도·강도를 측정한 것이 아니다. 아래 1번 문제 검증에서 이 점을 분리해 다룬다.

## 1. 다섯 가지 기초 질문

### Q1. 문제 검증 — 정말 문제인가

| 문제 | 빈도 | 심각도 | 추세 | 증거 | 신호 |
|---|---|---|---|---|---|
| A. 리뷰 요청 PR을 놓치거나 늦게 본다 | 팀원 수 x PR 수, 매일 발생 가능 | 중: 병목은 되지만 막는 정도는 PR 대기 시간에 비례 | 팀·PR이 늘수록 악화 | 사용자 진술 [약, 1인] | **조건부 go** |
| B. 내가 안 건드리는 영역의 진행을 모른다 | 주 단위로 느낌 | 중~상: 불필요한 작업(README AS-IS)으로 직결 가능하나 이 프로젝트에서 실제 발생 건수 미확인 | 규모에 비례 | 사용자 진술 + README 서술 [약~중] | **조건부 go** |

관찰할 점:
- A의 "문제"는 GitHub이 이미 이메일/알림으로 푸시한다. 따라서 문제는 "알림이 없다"가 아니라 **"알림이 흩어져 있고 우선순위·대기 시간이 안 보인다"** 일 가능성이 높다. 이건 가설이다. 팀원이 GitHub 알림을 실제로 어떻게 처리하는지 모른다.
- B는 문제 자체의 증거보다 **"해결책이 이미 반쯤 만들어져 있다"**(아키텍처 페이지)는 사실이 더 강한 신호다. 만든 사람이 필요를 느꼈다는 간접 증거(약).
- 경고(solving a non-problem 위험): 두 문제 모두 사용자 1인 진술이 근거다. 팀원 2~3명에게 5분 질문이라도 하기 전에는 "확정된 문제"가 아니라 "유력한 문제"로 취급한다.

### Q2. 대상 — 누구인가

확정된 사실: 팀원 2~10명, 각자 PR을 올리고 서로 리뷰, 인증 없음 (`00-context.md`). 이 위에서 증거 없이 나눈 **작업 가설 세그먼트**:

| 세그먼트 | 맥락 | 이 제품에 원하는 것(가설) | 증거 |
|---|---|---|---|
| 리뷰어로서의 나 | PR이 몰릴 때, 다른 일 하다 중간에 확인 | "지금 내가 막고 있는 PR이 뭔가"를 빠르게 | [약] |
| 작성자로서의 나 | 내 PR이 누구에게서 대기 중인지 알고 싶음 | 내 PR의 리뷰 상태 | [약] **현재 범위 밖** (핵심 목적에 없음) |
| 다른 영역 담당자로서의 나 | 프론트 담당이 백엔드 흐름을 모름 | 영역별 변화의 요약 | [약] |
| 팀 리드/조율자(있다면) | 전체 병목 파악 | 영역·사람별 정체 | [약] 존재 여부 자체가 미확인 |

핵심 사실: 한 사람이 위 역할을 번갈아 한다. 즉 "페르소나"가 아니라 **"모드"** 다. 화면을 사람별로 나누기보다 질문별로 나누는 게 맞다 [약, 추론].

구조적 제약(코드): 서버가 사용자를 식별하지 않는다. `assignee_id`는 자유 문자열이고(`backend/tasks/models.py:18`), PR 동기화는 `WatchedRepo.github_login` 단위이며 없으면 서버의 `GITHUB_TOKEN` 계정으로 폴백한다(`pr_sync.py:11`). 그래서 "참여하는 모든 팀원이 각자 쓴다"(목적 1)를 만족하려면 **"나"를 정의하는 최소 수단**(예: 브라우저에 저장한 내 GitHub 로그인)이 필수다. 이는 UX 문제이자 데이터 모델 문제라 사용자 결정이 필요하다(§7 질문 1).

### Q3. 해법 적합성 — 이 형태가 맞는가

- 현재: 웹앱(SPA) + 3분 폴링(`DECISIONS.md` "조건부 폴링"). 팀원이 **브라우저 탭을 열어야** 본다.
- 리뷰 큐라는 목적 1은 "열어보지 않아도 알려주는" 채널(GitHub 알림, Slack 등)과 경쟁한다. 웹앱이 이기려면 **"열었을 때 지금 할 일이 첫 화면에 있다"** 는 가치가 알림보다 커야 한다.
- 목적 2(영역 흐름)는 "가끔 열어서 조망하는" 용도라 웹앱이 자연스럽다. 알림형은 부적합.
- 판단: **웹앱 유지가 타당** [약]. 단 두 목적의 사용 리듬이 다르다(1: 하루 여러 번 짧게, 2: 주 몇 번 길게). 한 화면에 섞지 말고 별도 진입점으로 분리한다. 푸시 알림/확장 프로그램은 이번 범위 밖(§5).
- 미확인: 팀원이 이 앱을 **언제** 여는지. 3분 폴링이 충분한지는 사용 패턴 없이 알 수 없다.

### Q4. 기능 검증 — 기능 집합이 맞는가

현재 기능을 두 목적 기준으로 판정(근거는 코드 존재 여부·구조, 사용 데이터 없음 → 전부 [약]).

| 기능 | 목적 1 | 목적 2 | 판정 |
|---|---|---|---|
| 감시 레포 + PR 자동 동기화 | 필수 | - | **유지** |
| PR 태스크의 대기 시간·요청자·변경 규모 | 필수(현재 없음, `00-context` P1) | - | **추가** |
| PR 상태 갱신(머지/닫힘/재요청 반영) | 필수 | - | **추가 검토**. 현재 동기화는 최초 1회 생성만 한다(`SeenPullRequest`로 중복 차단, `pr_sync.py:13-24`). 머지된 PR이 "할 일"에 남을 수 있다 |
| "나" 필터 / 내 리뷰 큐 | 필수 | - | **추가** |
| 아키텍처 그룹별 변경 흐름 | - | 씨앗 | **유지·확장** |
| 칸반 | 부분(상태 이동) | - | **통합** |
| 리스트("모든 작업") | 부분 | - | **통합**(칸반과 중복) |
| 분석 탭 | - | 부적합 | **폐기** |
| 활동 피드 | - | 부분 | **재정의 후 통합** |
| AI 체크리스트 생성(Groq) | 리뷰 보조 가능 | - | **보류**. 핵심 목적 어디에도 직접 안 나옴, 단 README의 TO-BE 핵심이라 사용자 결정 필요(§7 질문 3) |
| 수동 태스크 생성/서브태스크/역할 리뷰 | ? | ? | **보류**. 사용자가 PR 외 작업을 실제로 쓰는지 미확인 |

핵심 긴장: README의 정체성은 "작업 기록과 의사결정 회상"(`README.md:16-24`)이고, 이번 목적 1·2는 "리뷰 큐와 프로젝트 조망"이다. **제품의 중심축이 이동하고 있다.** 이 이동을 명시적으로 인정하지 않으면 기능 비대화(feature bloat)가 된다.

### Q5. 경쟁·대안 — 무엇이 다른가

| 대안 | 그들의 논지 | 우리 목적 1(내 리뷰 큐) | 우리 목적 2(영역 흐름) | 전환 비용 |
|---|---|---|---|---|
| GitHub PR 알림·"Review requests" 페이지 | PR이 있는 곳에서 직접 처리 | **직접 경쟁, 강함**. 이미 정확하고 실시간 | 해당 없음 | 0(이미 사용 중) |
| GitHub Projects | 이슈/PR을 보드·표로 계획 | 부분. 리뷰어 기준 뷰 구성 가능하나 설정 필요 | 부분. 커스텀 필드로 영역 구분하려면 수동 라벨링 필요 | 낮음 |
| Linear | 이슈 중심 팀 계획, 영역은 팀/프로젝트/라벨 | GitHub 연동으로 PR 상태 반영(리뷰 요청 큐 기능 보유 추정, **미검증**) | 프로젝트/사이클 진행률은 **사람이 만든 단위**로 집계 | 높음(워크플로 전체 이전, 유료 플랜 고려) |
| Slack/메신저 GitHub 알림 | 대화 속 푸시 | 알림은 되나 정리·우선순위 없음 | 없음 | 0 |
| 아무것도 안 함(구두·메신저로 물어봄) | - | 현재 기본값일 가능성 높음 | 현재 기본값일 가능성 높음 | 0 |

주의: Linear/GitHub Projects의 현재 기능은 **이 문서 작성 시 외부 검증을 하지 않았다**(기억 기반, [약]). 설계 확정 전 최신 기능 확인이 필요하다.

우리가 다른 점(차별화 가설, 모두 검증 전):
1. **계획이 아니라 코드 변화에서 영역을 자동 도출**한다. Linear/Projects의 "영역별 진행률"은 사람이 이슈를 영역에 분류해야 집계된다. 우리 `architecture.py`는 파일 경로로 그룹을 규칙 기반 도출한다(`integrations/architecture.py:1`). 소규모 팀이 이슈 분류를 안 하는 경우에 이점이 있다. **단 트레이드오프**: 코드 디렉터리 그룹은 "기능 영역"이 아니다(§3의 핵심 문제).
2. **리뷰 큐와 영역 조망이 한 곳**에 있다. 단, 이건 GitHub 쪽 두 화면을 합친 편의 수준이라 약한 차별점이다.
3. 솔직한 결론: 목적 1 단독으로는 GitHub 기본 기능에 이길 근거가 약하다. **목적 2가 실질적 차별점**이고, 목적 1은 그 앱을 "매일 열게 만드는 이유" 역할을 할 때 가치가 있다 [약, 추론]. 이 추론이 틀리면 전략이 바뀐다(§6 가정 A1).

화이트스페이스: "코드 활동에서 자동 도출한 영역 흐름 + 내 리뷰 큐"를 의견 없이 가벼운 도구로 제공하는 위치. 크기는 모른다.

**루프백**: Q5에서 목적 1의 차별화가 약하다고 나왔으므로 Q1(문제 A의 심각도)로 돌아가 "GitHub 알림으로 충분하다"를 팀원에게 확인해야 한다. 이게 가장 싸고 가치 높은 조사다.

## 2. 핵심 목적 2가지를 검증 가능한 가설로

### H1. 리뷰 큐 (목적 1)

> **만약** 팀원이 앱을 열었을 때 첫 화면에서 "내가 리뷰어로 지정된 미처리 PR"이 대기 시간 순으로 보인다면, **그러면** 리뷰 요청에서 첫 리뷰까지 걸리는 시간이 줄고 "놓친 PR"이 줄어든다. **왜냐하면** 현재 병목은 알림 부재가 아니라 "무엇이 나를 기다리는지 한눈에 안 보이는 것"이기 때문이다. (가정 A1, A2)

성공 신호(앱 내 측정 가능 / 정성 구분):

| 신호 | 측정 | 목표(초안, 기준선 없음 → 가설) |
|---|---|---|
| 첫 화면 도달 후 "내 리뷰 대기 PR 수"를 답하는 시간 | 관찰 테스트 5명 | 5초 이내, 5명 중 4명 |
| 리뷰 요청 → 첫 리뷰 시간 | GitHub API 타임스탬프(요청 시각, 첫 리뷰 시각) | 도입 전 2주 기준선 대비 개선. **기준선부터 측정해야 함** |
| 주간 활성 팀원 비율 | 앱 접속(익명 카운트 가능 시) | 팀원의 과반이 주 3회 이상 |
| 정성: "GitHub 알림 대신 이걸 먼저 본다" | 2주 후 팀원 5분 인터뷰 | 과반 |
| 반증 신호 | 팀원이 앱을 열지 않고 GitHub만 계속 사용 | 2주 후 주간 활성 < 1/3 이면 H1 기각 |

데이터 최소 수집 원칙(`00-context.md`)과 충돌하지 않게, 접속 측정은 개인 식별 없이 집계 또는 생략하고 정성 인터뷰로 대체해도 된다.

### H2. 영역 흐름 (목적 2)

> **만약** 팀원이 자신이 직접 관여하지 않는 기능 영역의 최근 흐름(무슨 일이 일어나고 있고, 정체/가속/비어 있는지)을 추상화된 시각 요소로 볼 수 있다면, **그러면** 다른 영역의 진행에 대한 이해가 올라가고 "예상과 다른 결과물을 받아 헛수고하는" 일이 줄어든다. **왜냐하면** 지금은 그 정보를 얻으려면 사람에게 묻거나 PR을 직접 열어봐야 하기 때문이다. (가정 A3, A4)

성공 신호:

| 신호 | 측정 | 목표(초안) |
|---|---|---|
| 이해 테스트: 내가 안 만진 영역 2곳에 대해 "지금 활발한가, 막혔는가, 무엇이 바뀌고 있는가"를 화면만 보고 답하게 하고 실제와 대조 | 5명, 30분 이내 | 정답률 4/5 이상 |
| 화면 해석 시간 | 같은 테스트에서 영역당 응답 시간 | 30초 이내 |
| 행동 변화(정성) | "이걸 보고 누군가에게 물어보거나 내 작업 방향을 바꾼 적이 있나" | 4주 안에 1건 이상 구체 사례 |
| 반증 신호 | 팀원이 "그래서 뭘 하라는 거냐/이미 아는 내용"이라고 반응 | 다수면 H2 기각 또는 영역 정의 재검토 |

헛수고 감소(README의 본래 문제)는 직접 측정이 거의 불가능하다. 건수가 적고 원인 귀속이 어렵다. 그래서 이해 테스트와 사례 수집으로 **대리 지표**를 쓴다. 이 한계를 명시한다.

## 3. "기능 영역별 진행 상황을 추상화해 시각화"가 보여줘야 할 것

### 먼저 풀어야 할 정의 문제

"기능 영역"은 현재 코드에 **존재하지 않는 개념**이다. 가장 가까운 것은 아키텍처 페이지의 그룹인데, 이는 디렉터리 경로로 나눈 것이다(`architecture.py:1`, 종류는 `backend/frontend/infra/docs/other`, `types/index.ts:64`). 예: "backend/tasks", "frontend/components". 이 둘의 차이:

- **코드 그룹** = 파일이 어디 있는가 (기술 계층 중심)
- **기능 영역** = 사용자에게 어떤 능력인가 (예: "AI 체크리스트", "PR 동기화", "아키텍처 뷰")

팀원이 "다른 부분의 진행"이라고 말할 때 어느 쪽을 의미하는지 **모른다**. 이 정의가 시각화의 모든 것을 좌우하므로 가장 큰 열린 질문이다(§7 질문 2).

또한 현재 코드 그룹에는 "진행"이 없다. 있는 것은 **커밋·파일 변경 수(활동량)** 와 `rising/steady/quiet` 추세(`types/index.ts:65-85`)뿐이다. **활동량 ≠ 진행.** 커밋이 많다는 건 진척일 수도, 같은 곳을 계속 고치는 헤맴일 수도 있다. 이 구분을 화면에서 속이지 않는 것이 전략상 중요하다.

### 안 A. 활동 흐름 지도 (코드 그룹 기준, 현재 데이터로 가능)

- **단위**: 코드 그룹(디렉터리 도출)
- **상태**: 활발함(rising) / 꾸준함(steady) / 조용함(quiet) + 마지막 변경 시점
- **답하는 질문**: "최근 어느 쪽에서 작업이 일어나고 있나? 어디가 멈춰 있나? 어떤 영역이 함께 바뀌나(결합)?"
- **강점**: 새 데이터 수집 불필요, 이미 구현된 씨앗, 사람이 분류할 필요 없음, 항상 최신
- **약점**: "진행"이 아니라 "움직임"만 보인다. 그룹 이름이 기술 계층이라 비개발 관점이 어렵다. 목표 대비 어디쯤인지는 알 수 없다
- **증거 요건**: 구현은 가능. 팀원이 이걸 "진행 상황"으로 받아들이는지는 미검증

### 안 B. 영역별 작업 상태 분포 (작업·PR 기준)

- **단위**: 영역(= 태스크의 `category` 같은 분류 또는 PR이 건드린 코드 그룹을 영역에 매핑)
- **상태**: 영역마다 작업을 `할 일 / 진행 중 / 리뷰 대기 / 완료` 분포로 요약 + 가장 오래 대기 중인 항목의 대기 시간
- **답하는 질문**: "그 영역에서 몇 건이 흐르고 있고, 어디서 막혀 있나? 리뷰 대기에서 정체되나?"
- **강점**: "진행"에 직접 답한다(상태 기반). 병목이 리뷰라면 목적 1과 연결되어 두 목적이 한 이야기가 된다
- **약점**: 태스크가 영역에 붙어야 한다. 현재 `category`는 자유 문자열이고 PR 태스크는 `'Review'`로 고정이다(`pr_sync.py:34`). 즉 **PR 태스크는 영역 정보가 없다.** PR이 변경한 파일 경로로 영역을 추정하는 새 로직이 필요하다(추측: GitHub API로 PR 파일 목록을 가져와야 함, 미확인). 리뷰 요청된 PR만 들어와서 팀 전체 작업의 일부 표본이다
- **증거 요건**: 영역 분류 방식 확정 + PR→영역 매핑 가능성 확인 필요

### 안 C. 영역별 한 줄 서사 (의미 요약)

- **단위**: 영역 + 최근 기간(예: 지난 7일)
- **상태**: 사람이 읽는 변화 요약(예: "인증 흐름 PR 2건 머지, 1건 리뷰 대기 5일") + 보조 시각 요소(스파크라인·상태 점)
- **답하는 질문**: "그 영역에서 최근 무슨 일이 있었나?" (누가 무엇을 바꿨는가의 의미)
- **강점**: 이해에 가장 가깝다. 커밋 로그와 PR 제목에서 LLM 요약 가능(Groq 이미 도입)
- **약점**: 요약 품질·사실 오류 위험(LLM 환각), 시각화보다 텍스트 중심이라 "시각화 필수" 조건과 충돌할 수 있다. 비용·지연도 추가
- **증거 요건**: 요약이 신뢰 가능한지 별도 검증 필요

### 비교와 추천

| 기준 | A 활동 흐름 | B 상태 분포 | C 한 줄 서사 |
|---|---|---|---|
| "진행"에 답하는가 | 낮음(움직임) | **높음** | 중 |
| 현재 데이터로 가능 | **예** | 부분(영역 매핑 필요) | 부분(LLM) |
| 시각화 필수 조건 | 충족 | 충족 | 약함 |
| 목적 1과 연결 | 약함 | **강함** | 약함 |
| 신규 위험 | 낮음 | 중 | 높음 |

**추천: A를 기반으로 B의 "정체 신호"를 얹는 단계적 접근.**

1. **1단계(A, 즉시 가능)**: 코드 그룹별 활동 흐름. 단, 화면에서 "진행"이라 부르지 말고 "활동"이라 부른다. 용어가 진실을 말해야 한다.
2. **2단계(B의 최소판)**: 각 그룹에 "리뷰 대기 중인 PR 수와 가장 오래된 대기 시간"만 붙인다. 이 한 가지가 활동량이 못 주는 정체 정보를 주고, 목적 1과 목적 2를 한 데이터로 잇는다.
3. **C는 이번 범위에서 제외**. 요약 신뢰성을 검증하기 전에는 도입하지 않는다.

이유: 지금 가장 싼 방법으로 H2를 시험하려면 A로 충분하다. A를 팀원에게 보여줘서 "이걸 진행 상황으로 이해하는가, 아니면 영역 정의가 틀렸는가"를 먼저 알아내는 게 순서다. B로 곧장 가면 영역 정의 문제(§7 질문 2)를 해결하지 않은 채 새 데이터 모델을 만들게 된다.

## 4. 범위 — will-do / will-not-do

원칙: **두 목적 중 하나에 직접 답하지 못하면 1급 화면이 될 수 없다.**

### Will do (이번 단계)

1. **"내 리뷰" 화면을 첫 진입점으로**: 내가 리뷰어인 미처리 PR 목록, 대기 시간 순. PR 전용 정보(요청자, 대기 시간, 변경 규모 가능하면) 표시. (H1)
2. **"나" 식별 최소 수단 정의**: 인증 도입이 아니라, 누구의 큐인지 정하는 수준. 방식은 사용자 결정 필요.
3. **프로젝트 흐름 화면**: 현재 아키텍처 페이지를 승격하고 이름을 사용자 언어로 바꾼다. 안 A + 대기 PR 신호. (H2)
4. **칸반·리스트를 하나로 통합**: 같은 데이터의 두 보기라 한 화면에 보기 전환으로 통합하거나 한쪽을 폐기. 어느 쪽을 남길지는 디자인 단계(`/journey`) 결정, 전략상 요구는 "1급 메뉴 하나".
5. **PR 상태 최신화 검토**: 머지·닫힘 PR이 할 일에 남지 않는 방안(백엔드 영향, 별도 결정).
6. 접근성·용어 통일·가짜 장식 제거는 디자인 단계 필수 요건으로 승계(`00-context.md` P1/P2).

### Will not do (명시적 거부, 이유 포함)

## 7. 사용자 결정이 필요한 질문
