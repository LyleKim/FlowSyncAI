# 07. 설계 단계 점검: 경화(fortify) · 포용(include) · 용어/문구

대상: `04-information-architecture.md`, `05-user-journeys.md` (+ 00~03 참조). 방법론: Intent `fortify`, `include`, `articulate` 관점.
**방법 고지**: 구현 전 설계 문서 리뷰다. 렌더링·보조기술 실측·사용자 조사 0건. 대비 비율은 Tailwind 기본 팔레트 hex로 내가 계산한 값이며(구현 시 실측으로 대체), WCAG 2.2 AA를 기준으로 했다. 제품 코드는 보지 않고 03·02의 줄 번호 인용에 의존한다. 평가하지 않은 것: 실제 GitHub API 응답(레이트리밋 헤더 등)은 GitHub 일반 동작에 대한 내 이해(확인 필요)이고, 모바일·다국어는 범위 밖.

## 0. 총평

05의 J4(E1~E14)는 이미 강하다. "없음"과 "못 가져옴"을 분리하고 신선도를 상시 노출한다는 원칙(§4.1)을 그대로 지켜야 한다. 이 문서가 더하는 것은 05가 놓친 **조용한 실패 경로 6개**(§1.2)와 접근성 요구(§2)다. 가장 위험한 한 가지: **서버가 GitHub 동기화에 실패해도 브라우저의 `GET /tasks/`는 200/304로 성공한다.** 그러면 화면은 "정상, 방금 확인"인데 실제 데이터는 오래됐다. 05 E3는 이를 `sync-prs`의 `errors`에만 의존해 감지하므로, 그 응답을 받지 못하는 경우(백그라운드 탭, 다른 팀원이 트리거한 동기화)가 구멍이다.

보호할 것(positive): 없음/실패 분리 원칙, 신선도 상시 표시, 롤백+알림 계약 요구(§4.1-6), "오류 아님: 이미 감시 중" 처리(E12), 점수 압박 거부(§7), `architecture/*`의 기존 aria·키보드 구현(03 §5.1).

### 1.3 최소 백엔드 계약 (UI가 성립하려면, 구현 스펙은 Rune/blueprint 몫)

UI R1~R3, R8, R10이 의존하는 데이터만 적는다. 구조는 정하지 않는다.
- 레포별 `lastSuccessAt`, `lastAttemptAt`, `lastError{kind: auth|rate_limit|not_found|upstream|unknown, resetAt?}`.
- 검색 결과가 상한에 닿았는지(`truncated`).
- 동기화 단일 실행과 최소 간격을 서버가 보장(클라이언트 호출 횟수에 비의존).

### 1.4 배경 갱신과 사용 중 목록 (F9)

3분 폴링과 탭 복귀 동기화는 읽는 도중 행을 옮긴다("내가 리뷰함" 이동, 05 J2-5). 규칙:
- 포커스 또는 호버가 행에 있는 동안 그 행은 **이동·삭제하지 않는다**. 대신 변경은 상단 "업데이트 2건 · 반영하기" 버튼 뒤에 쌓는다. 사용자가 직접 "지금 확인"을 눌렀을 때는 즉시 반영.
- 반영하며 포커스가 있던 행이 사라지면 포커스를 다음 행(없으면 목록 제목)으로 옮긴다. 포커스가 `body`로 떨어지면 실패다.
- 스크롤 위치를 유지한다(위에 삽입해 밀어내지 않는다).

### 1.5 첫 실행(J1) 점검

- 좋은 점: 가치(큐) 전 입력을 한 칸으로 제한, J1-b에서 레포 추가 생략.
- 구멍: 3단계 레포별 진행 표시(J1 §1.3)가 스크린리더에 전달되려면 §2.6 live region 규칙 필요. 로그인을 *왜* 묻는지 한 줄은 필수(05 워크스루 1단계 △). 입력은 실패해도 지우지 않는다.
- 합류자 경로(J1-b)는 백엔드 P3 선행이다. 선행이 없으면 J1-a만 동작하므로, 그 경우에도 "레포 추가 409"는 오류가 아니라 성공으로 이어지게(E12).

## 2. INCLUDE (WCAG 2.2 AA)

### 2.1 현황 기준선 (03 §5)

모달 role/Esc/트랩/포커스 복귀 없음, 클릭 가능한 `<div>` 3곳(키보드 불가), 아이콘 버튼 `title`만, `label`-`input` 연결 0건, 10px 이하 48곳, `lang="en"`, `h1` 중복, `motion-reduce` 0건, 반응형 없음. 반면 `architecture/*`와 `WatchedReposPanel`의 일부는 이미 양호하다. **새 설계는 이 기준선을 깨끗이 넘는 것이 아니라 "전 화면이 architecture 수준"이 되도록 해야 한다.**

### 2.2 키보드 조작과 "드래그 대체 수단"

확인된 사실: 03에 따르면 현재 칸반은 드래그가 아니라 버튼(`moveLeft/moveRight`)과 상태 `<select>`로 이동한다. 드래그 앤 드롭은 코드에 없다. 그러므로 WCAG 2.5.7(드래깅 대체)은 **신규 도입 시에만** 문제가 된다. 설계 결정을 문서로 못박는다.

- 00 결정 12로 PR 항목의 수동 이동은 없어진다. PR 큐에는 드래그·상태 변경 컨트롤이 전혀 없다. 큐의 모든 조작은 링크/버튼(GitHub에서 리뷰, 행 펼침, 정렬, 그룹 접기)이다.
- 전체 작업의 **보드 보기**(수동 작업)도 드래그를 도입하지 않는다. 카드마다 "상태 변경" 컨트롤(네이티브 `<select>` 또는 메뉴 버튼)을 둔다. 나중에 드래그를 추가하려면 이 컨트롤이 대체 수단으로 이미 있어야 하고, 둘의 결과가 같아야 한다.
- 보드 열 구조: 열마다 제목(`h2`/`h3`)+개수, 카드는 목록(`ul`/`li`). 카드 전체 클릭 영역이 필요하면 제목을 `<a>`/`<button>`으로 만들고 CSS로 카드 전체로 확장한다(`<div onClick>` 금지, 03 §5.2).
- 이동 후 안내: "‘제목’을 리뷰 중으로 옮겼어요"를 polite로 알리고, 컨트롤의 포커스는 유지한다. 카드가 다른 열로 가서 DOM 위치가 바뀌면 이동한 카드의 같은 컨트롤로 포커스를 돌려준다.
- 단축키는 만들지 않는다(YAGNI). 만들면 2.1.4(단일 문자 단축키 해제 수단) 의무가 생긴다.
- 전역: 첫 포커스 요소는 "본문으로 건너뛰기" 링크, 탭 순서=시각 순서, 포커스 순서가 사이드바→본문, 패널 열림 시 §2.3.

### 2.3 상세 패널/모달 패턴

04는 작업 상세를 URL이 있는 오른쪽 패널로 바꿨다. 방향은 옳다(모달 폐기 → 포커스 트랩 부담 감소, 링크 가능, 뒤로가기). 다만 "패널"이 **오버레이인지 옆에 붙는 영역인지**에 따라 요구가 갈린다. 권고: **좁은 화면(리플로 400% 포함)에서는 전체 페이지 라우트, 넓은 화면에서는 목록 옆에 붙는 비모달 패널**.

| 형태 | 요구 |
|---|---|
| 비모달 패널(권고, `/tasks/:id`) | 열 때 포커스를 패널 제목(`h2`, `tabindex=-1`)으로 이동. 트랩 없음. `Esc`와 닫기 버튼으로 닫으면 포커스를 **연 행**으로 복귀. 패널은 `<aside aria-labelledby>` 또는 `region`. URL 변경은 `document.title`을 갱신하고 제목을 읽게 한다. 목록은 계속 조작 가능하므로 `inert`/`aria-hidden` 불필요 |
| 모달이 불가피할 때(삭제 확인, 이름 변경 등 짧은 것) | 네이티브 `<dialog>`+`showModal()` 우선(트랩·`Esc`·배경 비활성이 브라우저 기본). 직접 만들면 `role="dialog"` `aria-modal="true"` `aria-labelledby`, 배경 `inert`, `Tab` 순환, `Esc` 닫기, 닫으면 트리거로 포커스 복귀. 파괴적 확인은 `role="alertdialog"`. 초기 포커스는 가장 안전한 버튼(취소) |
| 레포 관리(`WatchedReposPanel`) | 04대로 설정 페이지로 이동하면 모달 하나가 사라진다. 이동 전까지는 `Esc`와 트랩을 갖춰야 한다(03: `role="dialog"`만 있음) |

닫기 `X`는 `aria-label="닫기"`와 44px 영역. 포커스가 가려지지 않아야 한다(2.4.11): 고정 배너·고정 헤더가 포커스된 행을 덮으면 `scroll-padding-top`으로 보정.

### 2.4 시각화: 비색상 인코딩과 텍스트 대안 (영역 흐름)

핵심 목적 2의 시각화가 보조기술 사용자에게 비어 있으면 그 사용자에게 제품의 절반이 없다. 현재 `architecture/*`는 `aria-pressed/expanded/label`과 SVG 노드 키보드 처리가 있어 출발점은 좋다(03 §5.1).

**비색상 인코딩** (1.4.1, 1.4.11)
- 영역 구분: hsl 동적 색(`utils.ts:6-24`)에만 의존 금지. 영역 이름을 **차트 옆 직접 라벨**(범례 매칭 불필요)로 붙이고, 색은 보조로 둔다. 영역 수가 8~10을 넘으면 색 구분이 불가능하므로 라벨과 정렬 순서가 1차 식별자다.
- 추세: "활발해짐/꾸준함/조용함"을 **텍스트+모양 다른 아이콘**(예: 위/가로/점선)으로. 색만으로 구분 금지.
- 정체 신호("조용함+리뷰 대기 있음", 05 §3.3-3)는 문구로 쓴다: "리뷰 대기 2건 · 최장 5일". 배지 색 단독 금지.
- "연결 끊김"(별칭 매칭 실패)은 텍스트 라벨.
- 차트 요소 대비: 막대/선/노드 경계 대 배경 **3:1 이상**(1.4.11). 막대 사이 구분은 간격 또는 윤곽선으로 보강. 다크/라이트 양쪽에서 실측.
- 툴팁/호버 정보는 **포커스에서도** 나오고, 닫을 수 있고(`Esc`), 호버 가능하며 사라지지 않아야 한다(1.4.13). 정보가 툴팁에만 있으면 안 된다.

**스크린리더가 영역 흐름을 읽는 방식** (1.1.1, 1.3.1)

차트 SVG 하나에 긴 `aria-label`을 붙이지 않는다. 읽기 순서를 이렇게 설계한다.
1. 페이지 `h1` "영역 흐름".
2. 요약 문단(실제 텍스트): "서버 연결 repo 기준 최근 30일, 커밋 최대 60개. 영역 7개. 활발해짐 2, 꾸준함 3, 조용함 2. 리뷰 대기가 있는 영역 3개, 최장 5일(백엔드 API)." 이것이 시각 사용자의 "한눈에"에 대응한다.
3. 영역 목록(`ul`): 한 영역이 한 `li`. 각 항목 한 문장: "백엔드 API, 활발해짐, 지난 주 커밋 12건, 마지막 변경 어제, 리뷰 대기 2건 최장 5일." 이름은 영역 상세 링크.
4. 스파크라인·막대 SVG는 `role="img"`로 두되 `aria-label`은 짧은 요약("최근 4주 커밋: 3, 5, 9, 12, 증가")만. 중복 낭독을 줄이려면 목록 문장에 이미 있으면 `aria-hidden="true"`로 가린다.
5. **"표로 보기"** 전환(또는 항상 있는 `<details>`): 영역×주 커밋 수 `<table>`(`caption`, `th scope`). 숫자를 정확히 알아야 하는 사용자와 스크린리더 사용자 모두에게 유효하다.
6. 결합 그래프(`CouplingGraph`)는 원형 배치라 선형 읽기가 불가능하다. 03에 순위 목록이 이미 있다: 이 목록을 **동등한 1차 표현**으로 승격한다("백엔드 API와 프론트 컴포넌트가 함께 바뀌었어요, 14회"). SVG 쪽은 보조로 `aria-hidden` 또는 키보드 탐색 가능한 노드 유지 중 하나로 정리하고 둘을 동시에 낭독시키지 않는다.
7. 영역 선택(강조 연동)은 `aria-pressed`(이미 있음) 유지. 선택하면 "백엔드 API 선택됨. 결합 영역 3개 강조"를 polite로 한 번.

**읽는 기준 안내문(범례)은 툴팁이 아닌 본문 텍스트**(05 §3.3-2). 스크린리더에도 동일하게 "활동은 커밋·파일 변경 기준이며 진행률이 아니에요"가 노출되어야 한다.

대비(내 계산, 구현 시 실측으로 대체):

요구: 본문·라벨·메타 텍스트는 라이트 `slate-600` 이상, 입력창 경계는 `slate-500` 계열. 상태 색은 **텍스트에는 어두운 변형**을 쓰고 밝은 단계는 채움에만 쓴다. 의미 색이 겹치는 문제(03 §2.1: 보통=amber=검토 중)는 색을 의미에 1:1로 재배정하고 반드시 텍스트를 동반한다. 다크 모드 토글이 실제로 동작하는지(03 §3-1 `@custom-variant` 가설)가 확정되기 전에는 다크 대비를 검증할 수 없다. 다크는 실제 렌더에서 별도 측정.

글자 크기: WCAG에는 최소 px 규정이 없다. 그러나 03의 현황(본문 12px, 보조 9~11px, 48곳 10px 이하)은 가독성 문제이고, 200% 확대·저시력·한글(획 밀도가 높아 같은 px에서 라틴보다 작게 읽힘)에서 특히 나쁘다. 한글은 같은 크기에서 라틴보다 판독이 어렵다는 점은 일반적 타이포 상식에 근거한 내 판단이다.
- **본문 14px 이상, 최소 크기 12px**. 12px 미만 텍스트 0건(9px·10px·10.5px·11px 클래스 제거). 우선순위·PR 배지·이니셜 같은 핵심 정보는 12px 이상, 대기 시간·PR 번호 같은 핵심 필드는 본문 크기.
- 한글 `line-height` 1.5 이상, `word-break: keep-all`(어절 중간 줄바꿈 방지), 한글에 `uppercase`·`tracking-wider` 사용 안 함(03 §2.3).
- 크기는 `rem`. 브라우저 글자 크기 설정과 200% 확대에서 잘리거나 겹치지 않는다(1.4.4). 텍스트 간격 확대(1.4.12: 줄 1.5, 문단 2배, 자간 0.12em)에서도 가려지는 내용 없음. 03의 고정 높이 카드(`h-[19.5rem]`, `h-72`)는 이에 걸린다.

### 2.6 포커스 표시와 상태 변화 live region

**포커스 표시** (2.4.7, 2.4.11, 1.4.11)
- 모든 상호작용 요소에 `:focus-visible` 2px 이상 윤곽, 인접 색 대비 3:1 이상, 요소와 2px 오프셋. 전역 스타일 하나로 정의하고 컴포넌트별 `outline-none`은 대체 링 없이 금지(03: 18곳 중 대체 미확인).
- 포커스된 요소가 고정 배너·헤더에 가려지지 않는다.
- 호버에서만 보이는 컨트롤(03: 삭제 버튼 `opacity-0 group-hover`)은 `:focus-within`에서도 보인다. 터치 환경도 고려해 항상 보이게 하는 것이 낫다.

**live region 규칙** (4.1.3) — 모든 화면에 공통 영역 2개만 둔다.
| 영역 | 용도 | 규칙 |
|---|---|---|
| `role="status"` (polite) | 동기화 결과 변화, 항목 이동, 동기화 중→완료, 정렬 변경 결과 | **변화가 있을 때만** 알림. 3분마다 "확인했어요"를 읽지 않는다. 여러 건은 묶어 한 문장("새 리뷰 요청 2건, 정리됨 1건") |
| `role="alert"` (assertive) | 사용자가 막 시도한 작업의 실패, 처음 발생한 동기화 실패 | 같은 실패는 **한 번만**. 배너는 사라지는 토스트가 아니라 화면에 남고, 폴링 때마다 재낭독 금지 |

추가:
- 상단 신선도 문구("3분 전 확인")는 live region으로 만들지 않는다(매분 갱신되어 소음). 필요 시 "지금 확인" 결과만 낭독.
- 토스트가 사라지는 경우 정보 손실이 없어야 한다(5초 이상 유지, 호버·포커스 중 유지, 중요한 실패는 배너로 남김). 자동 사라짐은 2.2.1 위험.
- live region 컨테이너는 **페이지 로드 시 DOM에 이미 존재**해야 낭독된다(나중에 삽입한 컨테이너는 놓칠 수 있음).
- 동기화 진행(J1 3단계): "레포 2개 중 1개 확인함" 형태로 완료 시점마다 polite. 스켈레톤에는 `aria-busy="true"`, 화면 준비 후 해제.
- `animate-pulse/ping/bounce`는 제거 방침(03 §4). 남기는 모션이 있으면 `prefers-reduced-motion`에서 정지, 5초 넘는 반복 모션은 정지 수단 제공(2.2.2). 행 이동 강조는 모션 없는 색·윤곽 변화로.

### 2.8 기타 AA 요구 (설계에 영향이 큰 것만)

- **리플로(1.4.10)**: 현재 고정폭 `w-64` 사이드바, 반응형 없음(03). 04는 "데스크톱 우선"이지만 AA는 400% 확대(= 320 CSS px 폭)에서 가로 스크롤 없이 읽혀야 한다. 사이드바는 좁은 폭에서 상단 내비/메뉴 버튼으로 접히는 최소 규칙이 필요(모바일 디자인이 아니라 리플로 준수). 표는 예외지만 PR 행은 표가 아니라 카드/목록 구조를 권장.

## 5. 구현 단계 체크리스트 (검증 가능한 문장)

각 문장은 예/아니오로 판정 가능하다. 도구: axe, 키보드, VoiceOver/NVDA, 브라우저 확대, 네트워크 차단(DevTools).

**상태·복구**
1. 서버 동기화가 실패한 상태(스텁)에서 큐 화면에 배너가 표시되고, 배너가 사라지는 토스트가 아니다.
2. 신선도 문구는 마지막 *성공* 시각이며, 실패한 시도 직후에도 값이 갱신되지 않는다.
3. `GET /tasks/`가 200/304여도 서버 보고 `lastSuccessAt`이 6분보다 오래되면 "오래됨"이 텍스트로 표시된다.
4. 검색 결과가 100건에 도달한 응답(스텁)에서 "일부만 가져왔어요"가 표시된다.
5. 큐 요약의 숫자와 목록의 대기 행 수가 같고, 숨긴 항목(초안·정리됨)은 개수와 함께 표시된다.
6. 401, 레이트리밋, 404 응답 각각에서 서로 다른 문구와 행동이 나오며, 401에서는 재시도 버튼이 없다.
7. 레이트리밋 상태에서 "지금 가져오기"는 `aria-disabled`이고 풀리는 시각이 같은 화면 텍스트로 있다.
8. 레포 1개만 실패한 응답에서 나머지 레포의 PR은 정상 표시되고 실패 레포 행은 삭제되지 않는다.
9. 가져온 건수 0 + 로그인이 후보에 없을 때 E5 빈 상태가, 정상 빈 큐(E7)와 다른 문구로 표시된다.
10. 로그인 입력 `@Octocat `, `github.com/OCTOCAT`이 `octocat`으로 정규화되어 비교되고, 후보의 원래 철자가 표시된다.
11. 큐 화면과 설정에서 "{login}의 큐"가 항상 보인다.
12. `localStorage`를 차단한 브라우저에서 앱이 예외 없이 동작하고 안내가 나온다.
13. 낙관적 갱신이 서버 오류로 실패하면 UI가 원래 값으로 롤백되고 오류 알림이 나온다(`console.error` 단독 처리가 0건).
14. 네트워크 차단 시 읽기 화면이 유지되고 쓰기 컨트롤은 이유와 함께 `aria-disabled`이다.
15. 오프라인 해제 시 자동 재가져오기가 일어나고 "다시 연결됐어요"가 한 번만 낭독된다.
16. 영역 활동 0건 화면에 "완료"라는 단어가 없고, 원인 3종이 서로 다른 문구다.
17. 포커스 또는 호버된 행은 배경 갱신 때 이동·삭제되지 않고 "업데이트 N건 · 반영하기"가 나타난다.
18. 포커스된 행이 사라질 때 포커스가 다음 행 또는 목록 제목으로 이동한다(`document.activeElement`가 `body`가 아님).
19. 공유 설정 저장 충돌(스텁 `updatedAt` 불일치) 시 입력값이 보존되고 충돌 알림이 나온다.
20. 연결된 레포 삭제는 확인 대화상자를 거치고, 본문에 "팀 모두에게 적용"이 있다.

**키보드·구조**
21. 마우스 없이 큐에서 "GitHub에서 리뷰" 링크 열기, 행 펼침, 정렬 변경, 그룹 접기를 완료할 수 있다.
22. `onClick`이 붙은 `div`/`span`이 0건이다(버튼·링크만).
23. 보드 보기에서 드래그 없이 카드의 상태 변경 컨트롤로 모든 상태 이동이 가능하다.
24. 첫 `Tab`이 "본문으로 건너뛰기"에 닿고, 활성화하면 `main`으로 포커스가 이동한다.
25. 라우트 전환 후 `document.title`이 바뀌고 포커스가 새 화면 `h1`(또는 `main`)로 이동한다.
26. 화면당 `h1` 1개, `main` 1개, `nav`에는 `aria-label`이 있다. `html lang="ko"`다.
27. 패널을 열면 포커스가 패널 제목으로 가고, `Esc`로 닫으면 연 행으로 돌아온다.
28. 모달(있다면)은 `role="dialog"`/`alertdialog`, `aria-modal`, `aria-labelledby`, 배경 비활성, `Tab` 순환, `Esc` 닫기, 포커스 복귀를 모두 만족한다.
29. 모든 입력은 `label for`/`id`로 연결되고, 오류는 `aria-describedby`+`aria-invalid`로 연결된다.
30. 아이콘 전용 컨트롤 전부에 `aria-label`이 있다(`title` 단독 0건).
31. 포커스 표시는 모든 상호작용 요소에서 2px 이상, 대비 3:1 이상이며, 대체 링 없는 `outline-none`이 0건이다.
32. 고정 배너·헤더 아래로 `Tab` 이동할 때 포커스된 요소가 가려지지 않는다.
33. 호버에서만 보이던 컨트롤이 키보드 포커스에서도 보인다.

**시각·텍스트**
34. 12px 미만 글자가 0건이고(`text-[9px]`,`[10px]`,`[10.5px]`,`[11px]` 검색 0건), 본문은 14px 이상이다.
35. 일반 텍스트 대비 4.5:1 이상, 큰 글자·UI 경계·차트 요소·포커스 링 3:1 이상이 라이트·다크 각각 실제 렌더에서 측정으로 확인된다(`slate-400` 본문 텍스트 0건).
36. 우선순위·상태·추세·정체 신호 각각이 색을 제거(그레이스케일)해도 텍스트나 모양으로 구분된다.
37. 영역 차트는 요약 문단과 영역 목록으로 같은 정보를 텍스트로 제공하고, "표로 보기"에서 영역×주 숫자가 보인다.
38. VoiceOver로 영역 흐름을 처음부터 끝까지 읽을 때 같은 영역이 차트와 목록에서 이중 낭독되지 않는다.
39. 툴팁 정보가 키보드 포커스에서도 나오고 `Esc`로 닫힌다.
40. 320px 폭(400% 확대)에서 가로 스크롤 없이 큐와 영역 목록을 읽을 수 있다. 200% 확대·텍스트 간격 확대에서 잘림이 없다.
41. 상호작용 요소는 24×24px 이상이며, 영역 칩·닫기 버튼은 44px 영역을 가진다.
42. 동기화 결과·항목 이동은 `role="status"`에서 변화 시에만 낭독되고, 같은 실패는 1회만 `role="alert"`로 낭독된다. 3분 폴링마다 낭독이 발생하지 않는다.
43. `prefers-reduced-motion`에서 모든 반복 모션이 정지한다. `animate-pulse/ping/bounce` 클래스 0건.
44. +/− 변경 규모, PR 번호, "외 N" 칩은 접근 이름이 문장으로 낭독된다(VoiceOver로 확인).
45. 제목은 말줄임으로 정보가 사라지지 않고 상세에서 전체가 보인다.

**용어**
46. UI 문자열에 "프로젝트 흐름", "감시", "동기화", "Accept", "업무", 영어 병기 `( … )`가 0건이다.
47. 동기화 버튼 문구 "지금 가져오기", 상태 문구 "N분 전 가져옴"이 모든 화면에서 동일하다.
48. "대기"는 큐 그룹명 "리뷰 대기"로만 쓰이고, 경과 시간은 "올라온 지 N일"(Q9 확정 전)이다.
49. 오류·빈 상태·확인 문구가 §3.2~3.4의 3요소 구조(무슨 일·영향·행동)를 따르고, 문장형 메시지는 해요체다.
